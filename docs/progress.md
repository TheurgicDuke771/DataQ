### Upstream 0-day triage — `bikini/exploitarium` (2026-07-24)

Triaged the public [`bikini/exploitarium`](https://github.com/bikini/exploitarium) archive (~44 PoCs, 12 assigned CVEs in its `cves.md`, the rest claimed unreported) against DataQ's actual dependency graph. **Verdict: not impacted — no code change warranted.** Recorded because *why* we are safe is not obvious from the code, and two of the reasons are conditions that could quietly stop holding.

The four entries that touch our stack and why each misses:

| PoC | Our reality | Why it misses |
|---|---|---|
| `redis-vset-duplicate-hnsw-id-rce` (RCE) | `redis:7-alpine` | The Vector Sets module ships from Redis **8**; 7.x has no `VSET`/`VLINKS` surface. Also needs an authenticated client — broker is internal-ingress + `--requirepass`. **→ [#980](https://github.com/TheurgicDuke771/DataQ/issues/980)** |
| `postgres-ri-owner-switched-cast` (RCE) | one least-priv `dataq_app` role | Needs a hostile DB role with `CREATE TYPE/FUNCTION/CAST` + `REFERENCES`, *and* a referenced-table owner in `pg_execute_server_program`. Neither exists; Azure Flexible Server does not grant the latter. |
| `curl-smtp-expn-recipient-crlf-injection` | `smtplib`, not libcurl (`alerting/email.py`) | Different code path — and our own analogous exposure is already closed: user-supplied recipients are CR/LF-rejected at write time by `_UNSAFE_IN_RECIPIENT` (`notification_service.py`, from the #639 review). |
| `flowise-mcp-env-case-bypass` | FastMCP **server** at `/mcp` | Flowise spawns stdio children from user config past a case-sensitive env denylist; we never spawn a child process from user input. |

That last one is a *class* rather than a package match — a case-sensitive allow/denylist matched against a case-insensitive value — so the three equivalents in our code were checked rather than assumed: webhook SSRF hosts lowercase both the config side (`notification_service.py:58`) and the parsed URL host (`:83`), and the workspace-admin allowlist matches case-insensitively (`auth.py:283`). All three are allowlists, so the failure mode is fail-closed either way.

Confirmed absent from the graph rather than eyeballed: Pillow, pycurl, pycares/aiodns, paramiko/ssh2, libarchive, Next.js (we are Vite). `nghttpx` and `docker cp` appear nowhere in the repo. The remaining ~35 PoCs are desktop or unrelated-server software with no intersection.

**Two caveats kept deliberately.** These are largely **unpatched**, so "not impacted" rests on non-intersection and missing preconditions — there is nothing to bump, and no green audit will ever confirm this the way `pip-audit` confirms a CVE. And the repo's technical claims were taken at face value; no PoC was run. Neither changes the verdict, since non-intersection holds whether or not the bugs are real.

### Upstream supply-chain triage — `ChainDrop` npm worm (2026-08-04)

Triaged the **ChainDrop** npm worm — a self-propagating Shai-Hulud derivative, first malicious publish `keyv@6.0.0` at **2026-08-04 09:35 UTC** (i.e. same-day), 1,300+ packages and ~2B monthly downloads, spreading by harvesting npm/GitHub tokens from install-time environments and re-publishing with them. **Verdict: not impacted — no code change warranted.** Recorded because this one is *unlike* the `bikini` triage above: all three headline packages **are** in our graph, so "not impacted" is a **version** claim, not an absence claim — and the thing holding it is a caret range.

| Package | Ours (lockfile + installed) | Malicious | Why it misses |
|---|---|---|---|
| `keyv` | 4.5.4 | 6.0.0 | Two majors below; arrives only under `flat-cache@4` |
| `flat-cache` | 4.0.1 | 6.1.24 | Two majors below; arrives only under `file-entry-cache@8` |
| `file-entry-cache` | 8.0.0 | 11.1.6 | `eslint@9` declares `"file-entry-cache": "^8.0.0"` — a caret on 8 **cannot** resolve to 11.x |

All three are transitive under ESLint; none is a declared dependency in `frontend/package.json`. The chain is `eslint@9 → file-entry-cache@8 → flat-cache@4 → keyv@4.5.4`, so the caret at the top pins the whole chain — **even an unpinned reinstall today lands on the same versions**. That is the real reason we are safe; the rest is corroboration: the lockfile last moved `2cf4f791` (2026-07-27, eight days before the attack) and is unmodified; all three frontend installs in `ci.yml` are `pnpm install --frozen-lockfile` (the one `npm install`, line 511, is exact-pinned dependency-free `semver@7.8.5`); and the lockfile has zero hits for the secondary-wave scopes (`@servicetitan`, `@onereach`, `@qlik`, `@picsart`, `@deliveroo`, `ornikar`, `cacheable*`, `cache-manager`, `ecto`).

**IOC sweep clean.** No `setup.mjs` / `Math_Symbol.js` / `math_init.js` / `gh-token-monitor.sh` in the repo or installed tree, no `preinstall` hook in any installed package (the payload fires from `preinstall`, so installation alone is enough — it never has to be imported), no `bun-dl-*` staging dirs, no `npm-cache.com` in shell history or `/etc/hosts`. Checked explicitly because **this strain targets AI-agent configs for re-infection**: it plants `.claude/setup.mjs` and `.vscode/tasks.json`, and harvests `.claude/` / `.cursor/` / `.anthropic/` credentials. Both directories are clean, here and in `$HOME`.

The `npx -y` MCP servers in `.mcp.json` were checked separately, since they are the one surface with **no lockfile** — they re-resolve at every launch. Both are clean: neither was republished in the attack window (`@upstash/context7-mcp` latest 2026-07-25, `@azure/mcp` latest 2026-07-31), and their dependency sets (`zod`, `undici`, `express`, `commander`, MCP SDK, platform binaries) do not include any affected package.

**No credential rotation performed, deliberately** — rotation is warranted on evidence of *execution*, and there is none. Worth stating because the standard incident advice is "rotate everything"; applying it without an execution signal would have meant re-minting the Key Vault `conn-*` set, and per the live-connections note one credential is N per-connection secrets that must each be re-tested or some silently stay dead.

**Two caveats kept deliberately.** (1) My `~/.npm/_cacache` scan returned nothing, **but so did the positive control** — that scan was *inconclusive*, not clean, and is not counted as evidence; the pnpm store is authoritative and it is clean. Recorded because an empty result from a scan that cannot hit anything reads identically to a real all-clear. (2) The protection is a **caret range, not a pin** — an ESLint major bump is exactly what would move `file-entry-cache` from `^8` into the `11.x` line, and Dependabot opens those automatically for npm. `pnpm audit --audit-level=high` is a merge gate, but advisory data for a hours-old worm lags it. This is not hypothetical right now: **5 npm Dependabot PRs (#1168/#1172/#1173/#1175/#1176) have been sitting open across the worm window** since 2026-08-03. Each was diff-checked rather than waved off — all five touch `pnpm-lock.yaml`, none contains a line touching `keyv`/`flat-cache`/`file-entry-cache`/`cacheable`, and none bumps `eslint`, so none can move the chain. Hardening (minimum-release-age policy, `--ignore-scripts`, pinning `@upstash/context7-mcp` to an exact version the way `@azure/mcp` already is) was **considered and consciously not taken** in this pass — so the next ESLint major is the event to re-check this note against.

### Inventory-sync failure visibility (2026-08-08)

[#1104](https://github.com/TheurgicDuke771/DataQ/issues/1104) (filed by the #1103 code review,
`v1.1 Backlog`) — an opted-in inventory sync (`config.inventory_sync`, ADR 0040) whose principal
can't read the enumeration query (UC: no `SELECT` on `system.information_schema`; Snowflake:
revoked INFORMATION_SCHEMA access) failed every daily tick invisibly: toggle on, connection test
green (the `SELECT 1` probe never exercises this query), zero assets ever appear, no surface says
why — the #828 shape again. Fixed by PR
[#1227](https://github.com/TheurgicDuke771/DataQ/pull/1227): three nullable `connections` columns
(`inventory_sync_last_attempted_at`/`inventory_sync_last_error`/`inventory_sync_failing_since`,
migration `c22fa93eb834`, mirroring the `lineage_last_*` pattern from #858) + a
`classify_inventory_sync_error` classifier that names the known system schema for a permission
failure + a connections-list "inventory sync failing" badge for opted-in, currently-failing
connections. Migration tested up/down/up locally against a real Postgres.

The `/code-review` pass on the PR found four real robustness defects in the bookkeeping — all
fixed in-PR, all mutation-checked (each new regression test was re-run against the un-fixed code
to prove it fails for the right reason). Every one turned a **per-connection** failure into a
**per-sweep** one, i.e. the fix for an invisible failure had itself acquired an invisible failure:
(1) the outcome `session.commit()` sat unguarded inside the per-connection `except`, so a
transient Postgres error on the bookkeeping write propagated out of the loop and skipped every
remaining connection; (2) `inventory_sync_failing_since` was a read-modify-write with no row lock,
so two overlapping sweeps both read NULL and both wrote their own "now", walking the START of a
failure streak forward and under-reporting how long a connection had been broken; (3) the except
block read `connection.type` and wrote back to the ORM instance immediately after
`session.rollback()` had expired it — a connection deleted mid-sweep (reachable: an admin deleting
it through the API) raised `ObjectDeletedError` and killed the task. (1)–(3) are the same shape
`orchestration_service.record_poll_failure` already solved for `consecutive_poll_failures`, so the
lock mechanism moved into a shared `services/connection_lock.py` rather than being written twice,
and the outcome write now re-fetches by id under `FOR UPDATE` and never raises. (4) the
PERMISSION classification was a broad substring match applied regardless of *when* the failure
happened, so a secret-store 403 or an expired token — failures that never reached the warehouse —
were reported as "missing SELECT grant on the system schema", sending an admin to fix a privilege
that was never the problem while the real fault stayed undiagnosed (a confident wrong answer, the
exact #828 shape this feature exists to end). The specific message is now gated on PHASE: only a
failure raised by the enumeration query itself (`InventorySyncEnumerationError`, wrapping nothing
but the phase) can claim a grant, and it hedges ("most likely … if the grant is already in place,
re-check the credentials"). Plus a minor: the three columns are now cleared when a connection opts
OUT of `inventory_sync` — at UPDATE time, not only in the daily sweep, since the sweep can't see
the toggled-off-and-back-on-between-ticks window and every reader would meanwhile be told "failing
since <old date>" for a sync nobody has attempted since.

A second review pass on the fixes found four more, all fixed in the same PR: the classifier's
generic fallbacks are written for a RUN, so an inventory failure rendered as "the run failed to
execute. See the server logs" (the answer #1104 exists to replace) and pointed at "the suite's run
target", which a sync does not have — `CONFIG`/`UNKNOWN` now have sync-specific wording while
`CONNECTIVITY`, already datasource-centric, stays shared; the grant message asserted more than the
phase gate can know (a Snowflake role that lost USAGE on its warehouse is rejected at the same
point and reads identically), so it now names the role/warehouse privileges alongside the SELECT
grant; and `deploy/README.md`'s operator row still documented the log-only behaviour. The one
finding deferred is [#1242](https://github.com/TheurgicDuke771/DataQ/issues/1242): Snowflake's
`INFORMATION_SCHEMA` is **privilege-filtered rather than access-denied**, so a role with no grants
enumerates ZERO ROWS instead of raising — which this PR records as a healthy sync, leaving the
Snowflake half of #1104 exactly where it started. Deferred rather than fixed because an
empty-by-design database enumerates zero rows too, so telling them apart needs a new state and a
UI decision, not a bug fix.

### Zero-table enumeration honesty (2026-08-09)

[#1242](https://github.com/TheurgicDuke771/DataQ/issues/1242) — the deferred half of #1104 above.
Fixed by PR #1258 (`fix/issue-1242-inventory-zero-table-enumeration`): the design decision left
open by the issue is implemented as the combined option — a persisted zero-table state **plus** a
transition signal, not reporting-only. Two more nullable `connections` columns (migration
`5ffa2405f9e8`, additive, tested up/down/up locally): `inventory_sync_last_table_count` (the row
count from the last SUCCESSFUL sync only — NULL = never synced, 0 = synced but nothing visible,
>0 = synced N tables; a failed attempt leaves it untouched, since it has no count to report) and
`inventory_sync_zero_since` (set only when the count DROPS from a previously-recorded N>0 to 0 —
the privilege-loss/dropped-database signal; held while it stays at 0, cleared on recovery above
0). A connection that has *always* enumerated zero never sets `_zero_since`, so it renders as a
neutral "0 tables found" note on the connections list rather than an error or warning — reusing
`inventory_sync_last_error` for this would just move the #828 "confident wrong answer" failure
mode to the opposite polarity. A genuine drop renders as a distinct "tables dropped to 0" warning
badge, gated on the sync currently NOT failing (so a stale count from before the sync started
erroring can't be read as the current state). `_record_sync_outcome` and `_has_sync_state`/
`_clear_opted_out_state` (the opt-out reset path) extend the existing #1104 bookkeeping rather than
duplicating it — same row lock, same never-raises contract. 8 new backend tests + 3 new frontend
tests, all mutation-checked (the fix reverted locally, the new tests confirmed to fail for the
right reason, the fix restored) per CONTRIBUTING discipline.

### Column ellipsis was inert in every table (2026-08-09)

[#1282](https://github.com/TheurgicDuke771/DataQ/issues/1282) — user-reported against live prod,
after this file and CLAUDE.md had both recorded the underlying defect as fixed. Fixed by PR
[#1283](https://github.com/TheurgicDuke771/DataQ/pull/1283).

The bounded-width + ellipsis + tooltip pattern shipped by #1185 (pipeline-runs "Failure reason")
and #1208 (run-detail "Observed") **had never worked, in any environment.** Not a stale deploy —
both were confirmed present in the live prod chunks (`Results-fEYNaYRi.js`, `RunDetail-8_xBzFNQ.js`).
Every DataQ table renders `scroll={{ x: 'max-content' }}`, which rc-table turns into
`width: max-content` on the `<table>`; a CSS intrinsic-sizing keyword sizes the table from its
content, which **neuters `table-layout: fixed`** and demotes the `<colgroup>` width to a
non-binding hint. Measured on the real component: a 260px-declared column rendering at **1917px**,
table 2969px wide. The fix bounds the **inner element** (`boundedTextStyle`) instead, which caps
the cell's max-content contribution however the table's own width resolves; applied to both
columns plus the Provider-run id, whose `Typography` `ellipsis` prop was inert for the same reason.

**Why three green suites never saw it, and the practice that came out of it.** The covering test
asserted `toHaveClass('ant-table-cell-ellipsis')` — antd *did* apply the class; the class simply
did nothing. jsdom performs no layout, so **no Vitest assertion can distinguish a working bound
from an inert one** — the same "a test that cannot express the failing case proves nothing" shape
as #520/#823/#953, in CSS rather than at a driver boundary. The unit tests now assert the bounding
style is applied (both mutation-checked) and the guard that it *works* is a pair of Playwright
measurements in `e2e/results.spec.ts`, comparing rendered vs. content width. Both were run against
the live app before push — which caught two defects in the assertions themselves: one measured the
hidden Runs table at 0px and could not fail, and one resolved to `ScalarValue`'s inline `<code>`
(scrollWidth 0) and would have failed in CI. The demo seed gained a full-length ADF error and a
real connector-error `observed_value`, because the short seeded values could not overflow the
bound. Review also caught that bounding the Provider-run id without a Tooltip left the column
identifying a run *worse* than unbounded (two Airflow runs from one day differ only in the clipped
tail) — fixed in the same PR.

**Standing practice this produced:** "merged" is not "deployed", and "deployed" is not "works".
Before reporting a fix as done, verify it is in the running artifact *and* that observed behavior
changed. CLAUDE.md §13's account of the 2026-08-09 deploy was corrected in the same PR — it had
recorded #1184 as already-live-and-working and #1208 as the only missing piece; both were wrong.
