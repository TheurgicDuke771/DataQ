# LLM / Agentic AI in Commercial Data-Quality, Observability & Catalog Products — Competitive Survey for DataQ

Research date: 2026-08-29. All claims are sourced from public vendor docs, blogs, and press as of this date; vendor AI features move fast, so treat this as a snapshot, not a permanent map.

---

## 0. TL;DR for DataQ

- **GX Cloud's ExpectAI is the closest direct comparable** (same GX-Core lineage as DataQ) and is the *only* vendor found with an unambiguous, documented "BYO your own OpenAI credential, we never touch your data" story that maps almost exactly onto DataQ's `LLMProvider` seam. Everyone else in the survey either (a) doesn't disclose BYO-model support at all, or (b) actively **standardizes on one hosted inference gateway** (Monte Carlo → AWS Bedrock) and instead documents *data-minimization* (schema/stats, not raw rows) as its privacy control rather than credential portability.
- **dbt Labs is the one other vendor with real BYOK breadth** — dbt Wizard supports OpenAI, Anthropic, AWS Bedrock, *and* Snowflake Cortex as swappable backends, with a stated Zero-Data-Retention policy and 90-day conversation-history retention (deletable). This is broader than DataQ's current Anthropic/OpenAI-compat/Ollama trio only in that it adds a warehouse-native model (Cortex) — worth noting as a future seam option, not urgent.
- **Local/self-hosted models (Ollama-class) are essentially unmentioned** across all ten observability/catalog vendors surveyed. Every vendor that discloses an architecture routes through a cloud model (OpenAI, Anthropic via Bedrock, Vertex/Mosaic/Cortex). DataQ's Ollama option is very likely closer to unique-in-category rather than table stakes — this is a real differentiator, not a checkbox to catch up on.
- **Validator-gated NL→SQL is not universal but is not rare either.** Soda, Atlan, and GX Cloud all document a "propose → human reviews/approves diff → applied" loop; Soda is explicit that generated actions are "scoped to the same operations you can perform yourself... subject to your role and permissions." None of the docs found describe an automated **read-only-enforcing SQL validator + dry-run** as a discrete, named component the way DataQ's design does — the pattern is "show a diff, let a human click approve," not "prove the SQL can't mutate/exfiltrate before it's ever run." This is a genuine gap in the market's disclosed designs and worth calling out as a DataQ strength.
- **RCA evidence-assembly is universal but almost never disclosed as a fixed, inspectable evidence set.** Monte Carlo, Sifflet, and Astronomer/Astro Observe all describe "gather lineage + logs + query history + code changes, then narrate," but none publish a deterministic, enumerable evidence contract the way DataQ's evidence card does (failing result + metric trend + same-run siblings + upstream pipeline run + lineage blast radius, assembled *before* any LLM narrative). The market pattern is "trust the agent's judgment about what to look at"; DataQ's design of computing the evidence deterministically and only handing a fixed bundle to the LLM for narration is closer to a defensible provenance/hallucination-containment story than anything found in public vendor docs.
- **Orchestration-layer signals (Airflow/dbt run status) ARE used by the two vendors that have real orchestrator integrations (Monte Carlo, Sifflet, Astronomer/Astro Observe, Metaplane/Datadog)** — but the disclosed use is shallow: "show DAG success/failure alongside data incidents" and duration/anomaly detection on task runtime. **None of the surveyed vendors document delay-vs-schedule-history baselining or env-mismatch detection between an orchestrator trigger and the environment a check actually ran in** — which is exactly the pair of things DataQ's `pipeline_runs` + `trigger_bindings` + near-miss detector already do. This looks like a genuine, checkable differentiator.
- **MCP adoption is now mainstream in this category**: Monte Carlo, Bigeye, Sifflet (in progress), Atlan, Elementary, and dbt Labs all ship or are shipping MCP servers. DataQ's 47-tool MCP surface is competitive in scale — Bigeye's hosted gateway exposes 56 tools, the high end found. What's *not* found anywhere else is DataQ's documented "honesty pass" discipline (the population/truncation/freshness/null-semantics audit baked into `mcp_gates.GATES` and the tool docstrings) — no vendor's public docs discuss LLM-facing honesty/blind-spot disclosure as a design axis at all.
- **AI-feature tier gating is mostly undisclosed.** Where it is disclosed (Monte Carlo's credit-based consumption pricing covers "a fleet of agents" inside all tiers; Anomalo's AIDA is "generally available for existing customers with an active subscription," not called out as a paid add-on), the trend leans toward **AI as included/bundled rather than a separate premium SKU** — vendors want adoption data, not a second sales motion, at least in the current earlier-adopter phase. No vendor was found gating basic NL-authoring behind a distinctly higher tier the way, e.g., enterprise seat-based SaaS often gates "AI Assistant" as an add-on.

## 1. Per-vendor findings

### 1.1 Great Expectations Cloud — ExpectAI

- **Rule/monitor suggestion inputs:** ExpectAI "performs deep analysis on a given Data Asset to set Expectations based on patterns in the data" — i.e., data profiling. It also generates **completeness Expectations that test whether null-value proportions deviate significantly from historical patterns** (so it consumes GX's own historical-run data, not just a single-snapshot profile). [Manage Expectations](https://docs.greatexpectations.io/docs/cloud/expectations/manage_expectations/), [ExpectAI docs](https://stork.ai... via search)
- **RCA/troubleshooting:** Not part of ExpectAI's disclosed scope — GX Cloud's AI story is authoring-side, not incident-side.
- **NL→SQL/NL→rule authoring:** ExpectAI "generat[es] SQL queries based on natural language prompts you provide and a data profile GX Cloud automatically provides" for custom SQL-based Expectations. Human-in-the-loop is explicit: users "carefully review and selectively approve only those rules that align with your specific data requirements and business context" before anything is applied. [GX ExpectAI blog](https://greatexpectations.io/blog/gx-expectai/)
- **BYO-model vs vendor-hosted:** **This is the standout finding.** GX shipped **BYO OpenAI credentials for GX Cloud Agent deployments** (~Feb 2026): "organizations [can] configure their own OpenAI credentials directly within their Agent environment to run ExpectAI securely using their own LLM account," explicitly so that "GX Cloud still cannot connect to or extract your underlying data." This is architecturally close to DataQ's `LLMProvider` seam — the credential and the data stay in the customer's own environment/account, GX's SaaS control plane never sees either. [Secure AI Data Quality for Agent Deployments](https://greatexpectations.io/blog/secure-ai-powered-data-quality-expectai-for-the-agent/)
- **MCP/agent interop:** Not found disclosed for GX Cloud specifically (GX Core is Python-library-based; no MCP server found in the search).
- **Premium tier gating:** Not disclosed either way in available docs.
- **Notable business context:** GX Cloud is being wound down as a standalone public product — FICO is acquiring GX Cloud and folding it into the FICO platform, with GX Cloud "no longer publicly available beginning June 1 2026." This makes ExpectAI's current design a snapshot of a product mid-transition, not a stable long-term target to benchmark against. [An Update for the Great Expectations Community](https://greatexpectations.io/blog/an-update-from-great-expectations/)

### 1.2 Monte Carlo Data

- **Rule/monitor suggestion inputs:** Not the primary AI story (Monte Carlo's core ML monitors are unsupervised-anomaly-based, not LLM-suggested); the LLM-facing story is entirely RCA/troubleshooting-side.
- **RCA/troubleshooting — the most thoroughly disclosed architecture in the survey:**
  - AI Agents (a **Monitoring Agent** and a **Troubleshooting Agent**, GA-track through 2026) investigate triggered alerts by "analyzing data changes, system failures, code updates, and lineage" to surface likely root causes, and **"Apache Airflow logs, dbt models, and other metadata related to an incident are made available in Monte Carlo, alongside additional root cause analysis capabilities"** — i.e., orchestration-layer signal is explicitly folded into the evidence set, not bolted on separately. [Root Cause Analysis](https://www.montecarlodata.com/platform/root-cause-analysis), [Airflow docs](https://docs.getmontecarlo.com/docs/airflow)
  - Interaction is conversational/multi-turn: users "ask follow-up questions and receiv[e] context-aware responses as investigations progress," and **"every completed Troubleshooting Agent analysis now automatically produces a remediation plan... a root-cause classification, a summary of what it proposes, and a recommended action"** — a structured output, not free text. [Remediation Agent](https://montecarlo.ai/blog-remediation-agent-ensures-every-analysis-ends-in-a-plan)
  - **Circuit Breakers**: an Airflow operator that polls a Monte Carlo-evaluated rule pre-pipeline-continuation and raises `AirflowFailException` on breach — this is the deepest orchestration-layer *action* (not just observation) found in the survey: the DQ platform can halt an Airflow DAG mid-run. [Circuit breakers](https://docs.getmontecarlo.com/docs/circuit-breakers)
  - Data inputs are agent-specific and minimized by design: "some AI Agents only need schema, table names, query patterns, and lineage with no data values required, while others work with statistics (row counts, null percentages, distributions) rather than individual records." [AI Architecture & Data Handling](https://docs.getmontecarlo.com/docs/ai-architecture-data-handling)
- **NL→SQL/NL→rule authoring:** Not the emphasis; Monte Carlo's AI story is RCA-first.
- **BYO-model vs vendor-hosted:** **Explicitly vendor-hosted, no BYO found.** "Monte Carlo standardizes on AWS Bedrock as the single inference gateway to keep customer data inside Monte Carlo's AWS environment under one consistent set of security and contractual controls," with Anthropic Claude and OpenAI models reachable *through* Bedrock (not via direct customer credentials). Encryption in transit/at rest (TLS 1.2+/AES-256), customer-managed KMS keys supported, **no training on customer data or prompts (contractually enforced with AI partners)**, and "prompt and input validation is enforced for all AI features to prevent prompt injection, adversarial manipulation, and data leakage." No customer choice of model provider or ability to point at a private/local model. [AI Security & Governance](https://docs.getmontecarlo.com/docs/ai-security)
- **MCP/agent interop:** A hosted remote MCP server at `https://integrations.getmontecarlo.com/mcp`, OAuth 2.1-authenticated, letting agents "investigate alerts, explore assets and lineage, create and manage monitors, and evaluate data quality." [MCP docs](https://docs.getmontecarlo.com/docs/mcp), [Meet MCP](https://www.montecarlodata.com/blog-mcp-data-ai-observability/)
- **Premium tier gating:** Pricing is consumption/credit-based across four tiers (Start/Scale/Enterprise/Business Critical); **"All tiers include Agent Observability, ML Observability, and Data Observability, plus a fleet of agents"** — AI agents are not a separate paid add-on, they're bundled (usage is metered via the same credit pool as everything else, so heavy AI use costs more but isn't gated by tier).

### 1.3 Alation

- **Rule/monitor suggestion inputs:** Alation's AI story is catalog/governance-centric (the "Alation Intelligence Operating System," AIOS) rather than DQ-rule-generation-centric; found no first-party disclosure of DQ-check suggestion from profiling.
- **RCA/troubleshooting:** Not disclosed as a distinct DQ-incident capability; Alation's agent story is search/discovery/governance automation.
- **NL→SQL/NL→rule authoring:** Not found disclosed for DQ checks specifically.
- **BYO-model vs vendor-hosted:** Not disclosed in available material.
- **MCP/agent interop:** Two separate surfaces: (1) **Alation Skills** — a plugin bringing catalog "Knowledge Layer" into Claude Cowork/Claude Code as structured instruction sets so an LLM "know[s] exactly how to query, explore, curate, and automate your data catalog" (announced March 2026, free); (2) the **Alation AI Agent SDK**, which exposes catalog search/discovery as MCP-compatible tools for building custom agents (beta → GA track). [Alation Skills](https://www.alation.com/blog/claude-data-catalog-introducing-alation-skills/), [AI Agent SDK](https://github.com/Alation/alation-ai-agent-sdk)
- **Premium tier gating:** Not disclosed.
- **Relevance to DataQ:** Low direct relevance (catalog/governance, not DQ-check authoring or RCA) — but the "Skills for Claude" pattern (structured, curated instruction sets rather than raw tool calls) is worth a passing note as an alternate interop shape beside MCP.

### 1.4 Soda

- **Rule/monitor suggestion inputs — "Contract Autopilot":** generates "fully populated contracts with recommended checks drawn from data profiles, reaching broad coverage in an afternoon instead of authoring contracts by hand for weeks." Inputs are explicitly **"dataset schemas, and non-identifiable column-level metadata"** — no mention of query-log or lineage input to suggestion (profiling-only, as far as disclosed). [Introducing SodaGPT](https://www.soda.io/resources/introducing-sodagpt), [AI for Data Quality](https://soda.io/blog/ai-for-data-quality)
- **RCA/troubleshooting:** Chat interface answers "questions about Soda and data" and provides "natural-language diagnostics," but no disclosed structured evidence-assembly pipeline comparable to Monte Carlo/Sifflet.
- **NL→SQL/NL→rule authoring — well-documented, closest analog to DataQ's own feature:** "Ask AI" turns plain-English prompts into production-ready SodaCL checks; **"Contract Copilot"** lets users iterate on contracts in plain English ("adding a freshness check, tightening a rule, handling a nested field") and shows users "exactly what changed" before it lands, maintaining human oversight. Guardrails are explicit: "system-level guardrails restrict responses to the intended Soda use cases," and generated actions stay "scoped to the same operations you can perform yourself in Soda Cloud, subject to your role and permissions" — i.e., an RBAC-bounded, diff-reviewed authoring loop, not an automated apply. [Ask AI docs](https://docs.soda.io/soda-v3/soda-cl-overview/ask-ai), [Soda AI docs](https://docs.soda.io/soda-ai)
- **BYO-model vs vendor-hosted — the second-most-explicit privacy design in the survey:** Uses "third-party foundation models (GPT-5 family)" by default, but supports **Bring Your Own Key (BYOK)**: "Soda only stores a reference to the key, never the key itself." Data minimization is explicit: **"Source data, such as row-level data and/or PII, is never sent by default"** to the model provider, and "API request data sent to the model provider is not retained for training." This is architecturally the closest match to DataQ's own no-raw-row / BYO-credential posture found anywhere in the survey.
- **MCP/agent interop:** Not confirmed in this pass (no first-party Soda MCP server found; searches surfaced only generic MCP explainer content).
- **Premium tier gating:** Not disclosed; Soda's public pricing shows a Team plan at $750/mo with a freemium option, but AI-feature-specific gating within that wasn't found.

### 1.5 Sifflet

- **Rule/monitor suggestion inputs:** **Sentinel** agent "reads metadata to identify blind spots and surface the most critical, failure-prone assets" using "metadata signals, from lineage and schema drift to usage patterns" — a coverage-gap/prioritization agent rather than a rule-generator per se.
- **RCA/troubleshooting — three-agent pipeline, the most explicitly staged multi-agent design found:**
  - **Sage** (diagnosis): "instantly connects lineage, logs, queries and change history to surface the real root cause," building "a living archive" that "consolidates related alerts into a single incident narrative."
  - **Forge** (remediation): turns Sage's diagnosis into "tailored recommendations based on past incidents and current system context," can push actions into Jira/ServiceNow or notify via Slack, and explicitly **"keeps humans in control"** during remediation (not autonomous action). Resolved incidents feed back into the knowledge base "to support faster RCA in the future" — an explicit incident-memory loop.
  - **Orchestration-layer input confirmed via separate integration docs** (not the agent-marketing page): Sifflet's Airflow integration surfaces DAGs in the catalog/lineage graph and lets you "quickly check the status (success/failure) of the latest run for each DAG directly throughout Sifflet"; a `SiffletDbtIngestOperator` sends dbt artifacts into Sifflet from within an Airflow pipeline step. So orchestration run status is available as lineage/catalog context feeding Sage's evidence-gathering, though the agent-specific marketing page itself doesn't spell out "we read your Airflow run status as RCA evidence" explicitly. [AI Agents Explained](https://www.siffletdata.com/blog/sifflet-ai-agents), [Airflow integration](https://docs.siffletdata.com/docs/airflow)
- **NL→SQL/NL→rule authoring:** Not the emphasized capability in available material (Sifflet's AI story is RCA/remediation-first, same shape as Monte Carlo).
- **BYO-model vs vendor-hosted:** Not disclosed.
- **MCP/agent interop:** MCP-based agent layer described as actively "launching soon" (as of the sourced blog) — intended to "expose diagnostic and remediation tools via tool calls," "inject pipeline metadata, user state, and logs as structured resources," and "maintain memory and context across multi-turn incident investigations." Not yet confirmed shipped/GA in this pass. [MCP: The Interface Layer](https://www.siffletdata.com/blog/model-context-protocol-the-interface-layer-for-intelligent-agents)
- **Premium tier gating:** Not disclosed (third-party pricing trackers cite an entry tier around $50k/yr, no AI-specific tier breakdown found).

### 1.6 Metaplane (→ Datadog Data Observability)

- **Rule/monitor suggestion inputs:** Automated quality monitors (freshness, volume, schema changes) are ML-anomaly-based on historical patterns, not LLM-generated from a prompt.
- **RCA/troubleshooting:** The **Airflow integration** is the clearest documented orchestration-layer signal use in the whole survey outside Monte Carlo: Metaplane "monitor[s] DAG and Task duration" using **ML-established baseline expectations for job execution time**, auto-creating incidents when actual runtime exceeds the predicted duration; it extracts lineage from queries run inside Airflow tasks, so a team can "quickly identify whether an Airflow job was the root cause of downstream issues like missed table updates or stale dashboards." This is duration/timing-anomaly detection at the *task* level, not a narrative LLM RCA. [Airflow integration blog](https://www.metaplane.dev/blog/airflow-integration)
- **NL→SQL/NL→rule authoring:** Not found as a distinct disclosed capability post-acquisition.
- **BYO-model vs vendor-hosted:** Not disclosed; now folded into Datadog's broader AI stack (Bits AI SRE), whose model-hosting posture wasn't investigated in this pass.
- **MCP/agent interop:** Not found for the data-observability product specifically (Datadog broadly has AI/agent tooling but nothing DQ-specific confirmed).
- **Premium tier gating:** Data Observability is now a Datadog product line; pricing/gating not investigated separately from core Datadog plans.
- **Notable:** Fully absorbed into Datadog branding as of the acquisition; "Metaplane" as an independent product no longer exists distinctly.

### 1.7 Anomalo

- **Rule/monitor suggestion inputs — "AIDA" (Intelligent Data Analyst):** a conversational data-analyst agent; "when data exploration surfaces something worth monitoring, AIDA turns discovery into action... directly from the conversation, users can create new data quality checks in Anomalo with no code required," with AIDA "recommend[ing] sensible defaults" and pre-filling configuration, then linking the new check back to the dataset. This is check-creation-from-conversation rather than proactive batch suggestion across a whole schema.
- **RCA/troubleshooting:** AIDA's framing is exploratory analysis + visualization ("instantly transforms answers into interactive visualizations... automatically selects the most effective chart") more than a dedicated incident/RCA pipeline; no structured evidence-bundle disclosure found comparable to Monte Carlo/Sifflet.
- **NL→SQL/NL→rule authoring:** AIDA generates "optimized SQL grounded in your enterprise context" for analysis and check creation, and explicitly "respects all access controls, governance policies, and data masking rules already in place."
- **BYO-model vs vendor-hosted — notably platform-routed rather than direct-provider:** AIDA "works seamlessly with Vertex AI, Mosaic AI, and Cortex AI, supporting models like Gemini and Claude" — i.e., it rides on the customer's *existing enterprise AI platform connection* (their Databricks/Snowflake/GCP AI service) rather than Anomalo brokering its own OpenAI/Anthropic account. This is a different flavor of "BYO" — BYO-platform rather than BYO-API-key — worth distinguishing from Soda/GX's BYOK model. [AIDA](https://www.anomalo.com/aida/)
- **MCP/agent interop:** Not found disclosed.
- **Premium tier gating:** "AIDA is generally available for existing Anomalo customers with an active subscription" — phrased as included with a subscription, not called out as a separate premium add-on, though the wording doesn't fully rule out tier-gating either.

### 1.8 Bigeye

- **Rule/monitor suggestion inputs — "Autometrics":** deploys "recommended data pipeline and data quality monitoring on every upstream column powering your data product," with coverage driven by **"usage patterns and downstream dependencies"** (i.e., lineage-graph-driven prioritization, similar in spirit to Sifflet's Sentinel) plus profiling-derived dynamic historical baselines for freshness/volume/schema/distribution. This is closer to "no-code automatic coverage" than "LLM reads a prompt and writes a rule." [Dependency Driven Monitoring](https://www.bigeye.com/blog/announcing-bigeye-dependency-driven-monitoring-and-lineage-plus)
- **RCA/troubleshooting:** "lineage-based root cause and impact analysis" is part of the core (non-LLM-labeled) product; the 2026 AI-specific push is "AI Trust Platform" positioning (below) rather than a named RCA agent.
- **NL→SQL/NL→rule authoring:** Not confirmed as a distinct disclosed feature in this pass (Bigeye's config story is YAML/API-first — "observability-as-code" — rather than NL-first).
- **BYO-model vs vendor-hosted:** Not disclosed.
- **MCP/agent interop — the largest surface found in the whole survey:** a **hosted MCP gateway** at `https://mcpgateway.bigeye.com/mcp` exposing **56 agent tools** (vs. 47 for DataQ) over the same REST surface (three OpenAPI 3.0 spec sets — Metadata, Observability, Sensitivity — covering 263 operations total). No local install needed; credentials passed as request headers. This is the single most directly comparable MCP-scale data point found. [Bigeye MCP Server](https://docs.bigeye.com/docs/bigeye-mcp-server)
- **Premium tier gating:** Not disclosed (no public pricing page with plan names found).
- **2026 repositioning:** Bigeye is rebranding around an **"AI Trust Platform"** — "AI Guardian" (runtime data-access policy enforcement for AI applications) and expanded PII/PHI/PCI sensitive-data classification, aimed at *governing AI systems' use of enterprise data* rather than *using AI to do DQ*. Distinct axis from the rest of the survey — worth noting as a category adjacent to, not overlapping, DataQ's current scope.

### 1.9 Acceldata

- **Rule/monitor suggestion inputs / RCA:** Acceldata's 2026 pitch is the most maximalist "agentic" framing in the survey — a **Data Quality Agent** that "finds, fixes, and prevents issues autonomously," powered by an "xLake Reasoning Engine" inside a "collaborative, agentic framework," plus a separate **Data Pipeline Agent** for pipeline lifecycle automation. Marketing language is heavy on autonomy ("build, run, and maintain pipelines") but the technical detail on *what specific evidence* each agent consumes (profiling vs. query logs vs. orchestrator run status) was not retrievable in this pass — a direct fetch of the Data Pipeline Agent page failed (TLS error), and search-result summaries stayed at the marketing-copy level. This is the weakest-verified vendor in the survey; treat the "autonomous" framing skeptically until a primary source with implementation detail is found.
- **NL→SQL/NL→rule authoring:** Not confirmed.
- **BYO-model vs vendor-hosted:** Not confirmed.
- **MCP/agent interop:** Acceldata separately advertises **"Agent & LLM Tracing"** — tracing "every prompt, model call, tool invocation, and retrieval step" for AI *applications built on top of* governed data — i.e., Acceldata positions itself as an observability layer *for* other people's agents (an AI-observability product), which is a different value prop than DataQ's own DQ-focused LLM features.
- **Premium tier gating:** Not disclosed.

### 1.10 Elementary Data

- **Rule/monitor suggestion inputs:** Elementary's core product is dbt-native, test-result/metadata-driven anomaly detection (row count, null rate, average value, etc., compared against historical baselines) — not LLM-suggested rules; "Elementary Cloud" adds "automated ML monitoring" and "a built-in catalog" on top of the dbt-native OSS test layer. AI agents are described as "scal[ing] reliability workflows for engineers and business users," but no first-party detail on what inputs those agents consume was found beyond that framing.
- **RCA/troubleshooting:** Not found as a distinct, named disclosed capability separate from its lineage/test-result model.
- **NL→SQL/NL→rule authoring:** Not found disclosed.
- **BYO-model vs vendor-hosted:** Not disclosed.
- **MCP/agent interop — confirmed and dbt-context-rich:** the **Elementary MCP Server** gives "AI agents and copilots access to trusted observability context without raw data access or manual scripts" — full test coverage, lineage, volume/freshness metrics, and incident management surfaced to Claude Desktop/Cursor/etc. The "without raw data access" framing is a data-minimization claim similar in spirit to Monte Carlo's and Soda's. [Introducing the MCP Server](https://www.elementary-data.com/post/introducing-the-mcp-server-observability-that-meets-you-where-you-are)
- **Premium tier gating:** Elementary is dual: a genuinely open-source self-hosted core (`elementary-data/elementary`, dbt package `dbt-data-reliability`) plus a paid Cloud tier with "premium features" — so the *baseline* product is free/OSS, and AI/Cloud-only features (the MCP server's cloud-context depth, ML monitoring) are plausibly the paid layer, though exact feature-by-feature gating wasn't itemized in available docs.

### 1.11 Atlan

- **Rule/monitor suggestion inputs — "AI-suggested rules":** Atlan AI "analyzes your asset's metadata and generates a list of suggested rules" via a "Suggest rules" action next to "Add rule"; typical suggestions are null counts, blank counts, freshness checks, duplicate detection, and volume checks, apparently profiling/metadata-driven (lineage, ownership, usage signals feed the broader Data Quality Studio, per Atlan's own description) rather than query-log-driven. [Use AI-suggested rules](https://docs.atlan.com/product/capabilities/governance/data-quality/how-tos/use-ai-suggested-rules)
- **RCA/troubleshooting:** Atlan's MCP-exposed "proactive data quality issue monitoring" and lineage traversal are positioned as giving an *agent* the context to reason about an issue itself (e.g., "an agent checking a column [gets] back provenance, quality score, governance policy, and ownership in one call") rather than Atlan running its own packaged RCA narrative pipeline — a meaningfully different shape from Monte Carlo/Sifflet's "we narrate the root cause for you."
- **NL→SQL/NL→rule authoring:** "Copilot can generate SQL-based rules from natural-language descriptions... tailored to your asset's context, including columns, data types, descriptions, database, and schema" — the same "suggest → human reviews → applies" shape as the rest of the field.
- **BYO-model vs vendor-hosted:** Not disclosed in material reviewed.
- **MCP/agent interop — Atlan's headline AI strategy, branded as "the Context Layer for AI":** the **Atlan MCP Server** gives agents (Claude, Cursor) the ability to search assets, run DSL filters, traverse lineage, and monitor quality with "full context and precision," explicitly positioned around **agents querying the lineage graph *before* they use data** — i.e., Atlan's framing treats its catalog as the trust/context layer *other* agents (including a DQ platform's own RCA agent) should consult, more than a DQ-check-authoring surface in its own right. [Atlan MCP](https://blog.atlan.com/announcements/atlan-mcp-ai-metadata/)
- **Premium tier gating:** Not disclosed.

### 1.12 dbt Labs

- **Rule/monitor suggestion inputs:** dbt's AI story is developer-workflow-centric (SQL/docs/tests/semantic-model generation), not DQ-monitor-suggestion in the observability-vendor sense; "dbt Copilot" does single-click generation of SQL/docs/tests/semantic models inside Studio/Canvas/Insights, grounded in the dbt project's own metadata.
- **RCA/troubleshooting:** Not the framing; **dbt Wizard** ("the new and recommended AI agent for governed data development in dbt") "handles the full development lifecycle — investigation, building, validation, and shipping — grounded in your dbt project's lineage, tests, contracts, and metric definitions," which is closer to an agentic dev-assistant than an incident-RCA tool.
- **NL→SQL/NL→rule authoring:** Central to the product — dbt Copilot/Wizard generate SQL, tests, docs, and semantic models from natural language, grounded in the project's own lineage/contracts/metrics as context.
- **BYO-model vs vendor-hosted — the broadest disclosed BYOK menu in the survey:** dbt Wizard supports **OpenAI, Anthropic, AWS Bedrock, and Snowflake Cortex** as swappable backends, usable "in the platform with managed or bring-your-own-key (BYOK) credentials, or in the terminal with your own key, with or without a dbt platform account." Explicit privacy commitments: **no training on customer prompts/conversation history/command results/feedback**; a **Zero Data Retention (ZDR) policy** with AI providers; API keys/tokens "not transmitted in raw form"; conversation history retained 90 days by default (deletable), feedback 400 days. This is the most explicit, most complete BYOK + retention-policy disclosure found in the entire survey, and the only vendor offering a *warehouse-native* model option (Cortex) alongside the two big hosted APIs. [Configure BYOK for dbt Wizard](https://docs.getdbt.com/docs/dbt-ai/wizard-byok), [dbt Wizard CLI data use and telemetry](https://docs.getdbt.com/docs/dbt-ai/wizard-telemetry)
- **MCP/agent interop:** The **dbt MCP server** ("dbt-labs/dbt-mcp") gives AI agents/copilots direct access to dbt-managed, governed, version-controlled data assets; a remote hosted variant runs inside dbt platform with no local install; VS Code/GitHub Copilot integration documented. [About dbt MCP](https://docs.getdbt.com/docs/dbt-ai/about-mcp)
- **Premium tier gating:** dbt Copilot/Wizard availability is tied to dbt Cloud/platform account tiers (exact tier-by-tier AI gating wasn't itemized in material reviewed, but the CLI's BYOK mode explicitly works "with or without a dbt platform account," i.e., there is a no-platform-subscription path to at least the CLI AI features if you supply your own key).

## 2. Orchestration-layer signal usage — cross-vendor summary (DataQ's specific ask)

This was the sharpest-focused question in the brief, so summarizing separately:

| Vendor | Orchestrator(s) integrated | What's disclosed as *used* | Depth vs. DataQ's design |
|---|---|---|---|
| **Monte Carlo** | Airflow (native provider), dbt | DAG success/failure surfaced alongside incidents; **Circuit Breakers** actively halt an Airflow DAG mid-run on a DQ-rule breach (bidirectional: DQ→orchestrator control, not just orchestrator→DQ observation); "Airflow logs, dbt models, and other metadata related to an incident are made available... alongside RCA" | Deepest *action* integration found (can stop a pipeline), but no disclosed delay-vs-schedule-history baselining or cross-environment (dev/qa/prod) mismatch detection |
| **Sifflet** | Airflow, dbt (via a dedicated `SiffletDbtIngestOperator`) | DAG success/failure status surfaced in catalog/lineage; dbt artifacts ingested per-run | Presented as catalog/lineage context, not explicitly wired into the RCA agent's evidence bundle in the docs found |
| **Metaplane/Datadog** | Airflow | **ML-baselined task/DAG *duration* anomaly detection** (closest thing found to "delay vs. history" reasoning, but at the task-runtime level, not a downstream freshness SLA) | Real statistical baselining exists here, closer to DataQ's own delay-vs-history concept than any other vendor, but scoped to Airflow task duration rather than DataQ's broader pipeline_run delay + trigger-binding env-mismatch model |

| **Acceldata** | Unclear (Data Pipeline Agent framed around pipeline lifecycle automation) | Not verifiable from available sources | Unverified |
| **GX Cloud / Soda / Anomalo / Alation / Atlan / Elementary / dbt Labs** | Not found as an RCA/monitor-recommendation input in this survey | — | These vendors' AI stories are authoring-side (rule/check generation) or catalog-side, not orchestration-signal-driven |

**Conclusion on this axis:** every vendor with a real orchestrator integration treats it as **either (a) a status/log feed shown alongside an incident, or (b) a duration-anomaly signal**, never as **(c) an explicit "was this run's delay abnormal relative to this pipeline's own schedule history" computation** or **(d) "did this trigger fire the check against the wrong environment"** the way DataQ's `trigger_bindings` + delay-vs-history + env-mismatch near-miss detector already do. This is a genuinely underexploited angle across the entire surveyed market — DataQ already has the schema (`pipeline_runs`, `trigger_bindings`) to make this concrete and inspectable rather than a vague LLM claim, which none of the surveyed vendors demonstrate having.

## 3. Is BYO/local-model + validator-gated output + honest evidence provenance actually rare? — verified

Breaking the brief's closing question into its three parts:

1. **BYO-model (any form) support:** confirmed for **GX Cloud (BYO OpenAI credential, Agent deployments)**, **Soda (BYOK, key-reference-only storage)**, **dbt Labs (BYOK across 4 providers incl. Bedrock/Cortex)**, and **Anomalo (BYO-*platform*, i.e., ride your own Vertex/Mosaic/Cortex connection)**. That's **4 of 12** vendors surveyed with *any* disclosed BYO story. The rest either standardize on a single hosted gateway (Monte Carlo, explicitly, via Bedrock) or simply don't disclose model-hosting architecture at all (Alation, Sifflet, Metaplane/Datadog, Bigeye, Acceldata, Elementary, Atlan). **So BYO is a real but minority pattern (~1/3) — DataQ is in good, not rare, company here, but is not the only one.**
2. **Local/self-hosted model support (Ollama-class, fully outside any vendor cloud):** **zero vendors** in this survey disclosed this. Every BYO story found is "bring your own *cloud API key*," not "point us at a model running on your own hardware with no external network call." **This is where DataQ is distinctive, not just "in good company."** Worth stating plainly in DataQ's own docs/positioning: local-model support for the LLM seam appears to be ahead of the disclosed state of the art in this category, not merely competitive with it.
3. **Validator-gated output (a distinct, provably-enforced read-only/dry-run gate on generated SQL, separate from "a human clicks approve"):** **not found as a named, discrete component anywhere in the survey.** Every vendor with NL→SQL (Soda, Atlan, GX ExpectAI, dbt Copilot) describes the same shape — generate, show a diff/preview, human approves, then it's applied through the product's own normal-user permission scope. That's a *social* gate (RBAC + review), not a *mechanical* one (a parser/validator that structurally guarantees the SQL cannot mutate data or exceed a read-only role before it is ever executed, independent of whether the human reviewing it actually reads carefully). **DataQ's read-only SQL validator + dry-run as an explicit, separately-named, enforced gate ahead of any human review is not something any surveyed vendor documents having** — this looks like a genuinely uncommon design choice worth keeping and calling out, not table stakes to catch up to.
4. **Honest evidence provenance (a deterministic, enumerable evidence bundle assembled *before* the LLM runs, with explicit blind-spot/limitation disclosure in the tool's own output):** **not found as a documented practice anywhere in the survey.** Every RCA vendor (Monte Carlo, Sifflet, Astronomer) describes "the agent looks at lineage/logs/queries/code and figures out the root cause" — evidence-gathering is *itself* part of the agent's autonomous judgment, not a fixed, auditable precondition to the narrative step. None of the reviewed docs mention anything resembling DataQ's MCP "honesty pass" — systematically auditing every tool's docstring/output for population/truncation/freshness/null-semantics blind spots and disclosing them in the field itself rather than only in prose. **This is the single clearest point of distinctiveness found in the whole survey.**

**Bottom line:** DataQ's overall posture (BYO/local + validator-gated + deterministic evidence + honesty-audited MCP surface) is **not merely rare — no single surveyed vendor was found combining even two of these four elements simultaneously**, let alone all four. GX Cloud is the closest on element 1, Soda is closest on elements 1+3 (BYOK + a review-gated authoring loop, though not a *mechanical* validator), and Monte Carlo/Sifflet are closest on evidence-richness for RCA (elements 4's *content*, not its *provenance discipline*). No vendor combines local-model support, a mechanical pre-execution validator, and disclosed evidence-blind-spot honesty.

## 4. ADOPT / IMPROVE / SKIP — mapped to DataQ's existing seams

### ADOPT (do these; the market validates them and DataQ isn't there yet, or has the seam but not the specific feature)

1. **Circuit-breaker-style orchestration action (Monte Carlo pattern), mapped to DataQ's `OrchestrationProvider` + `trigger_bindings`.** Today DataQ's orchestration seam is monitor + detect + trigger-on-success only (per CLAUDE.md §4 — deliberately no ADF/Airflow-as-datasource, and no "pause the DAG" action). Monte Carlo's Airflow Circuit Breaker operator proves there's a real, well-received pattern for a DQ platform to **stop a pipeline mid-run** on a rule breach. This would be a scope expansion beyond "monitor + trigger only," so it needs a considered ADR before building — flagging it as a validated pattern worth a design conversation, not a silent scope-creep.
2. **Duration/timing-anomaly baselining at the *task* level (Metaplane/Datadog pattern)**, complementing DataQ's existing pipeline-run delay-vs-history. DataQ already computes delay-vs-history at the pipeline-run level for the evidence card; Metaplane's ML-baselined *task*-duration anomaly (not just "did the whole DAG finish late" but "did *this specific task* run unusually long") is a finer grain worth considering for the `monitor_baselines` infrastructure DataQ already has (reused from the `anomaly` monitor kind, per progress.md).
3. **Explicit "evidence bundle" documentation/marketing framing.** No surveyed vendor publishes what's actually in their RCA context window as a fixed, named contract. DataQ's evidence card already *is* this; making the deterministic-evidence-before-LLM-narrative design an explicit, documented (and ideally testable/inspectable-by-the-user) contract is validated by its absence elsewhere as a real gap DataQ can own, not a redundant feature.
4. **A `catalog-constrained check suggestion` feature (already planned per the brief) should explicitly document its inputs** the way GX ExpectAI (profiling + historical run patterns) and Atlan/Bigeye (lineage + usage-pattern-driven prioritization) do — i.e., when it ships, state plainly whether it's profiling-only, lineage-prioritized, or both, since that's exactly the axis competitors differentiate on and half of them don't even disclose.

### IMPROVE (DataQ has the seam; sharpen it against what's now proven valuable elsewhere)

1. **RCA narrative — add a structured output, not just prose.** Monte Carlo's Troubleshooting Agent auto-produces a *structured* remediation plan (root-cause classification + summary + recommended action) alongside the narrative. DataQ's planned "LLM root-cause narrative on top of the evidence card" should consider emitting a similarly structured object (classification + action recommendation) rather than free text alone, so the UI/MCP surface can render/filter/act on it deterministically instead of parsing prose.
2. **Multi-provider BYO breadth.** dbt Wizard's inclusion of a *warehouse-native* model (Snowflake Cortex) alongside OpenAI/Anthropic/Bedrock suggests DataQ's `LLMProvider` seam (currently Anthropic/OpenAI-compat/Ollama) could eventually consider a Snowflake-Cortex or Databricks-native model path, given DataQ already has first-class Snowflake and Unity Catalog connections — this would let a customer route LLM inference through infrastructure they already trust and pay for, with zero new egress. Not urgent, but a natural extension of the seam's own design intent.
3. **MCP honesty as a documented, citable practice.** DataQ's `mcp_gates.GATES`-driven honesty audit is unmatched in the survey — but it's currently an internal engineering discipline (per progress.md), not a documented user-facing claim. Given the finding in §3 that no competitor discloses anything like it, this is worth surfacing in DataQ's own docs/marketing as a differentiator, not just an engineering habit.

### SKIP (validated elsewhere but wrong fit, or DataQ already deliberately declined the shape)

1. **"Autonomous agent takes action without review" framing (Acceldata's positioning).** Acceldata's marketing leans hardest into full autonomy ("finds, fixes, and prevents issues autonomously"); every *better-documented* vendor (Monte Carlo, Sifflet, Soda, GX) is explicit about human-in-the-loop gates. DataQ's existing validator-gated + dry-run + human-approve design is the more defensible pattern found in the survey — skip chasing Acceldata's autonomy framing.
2. **AI-observability-for-other-agents (Acceldata's Agent & LLM Tracing, Bigeye's AI Guardian).** Both vendors are pivoting part of their platform toward observing/governing *other* AI agents' use of enterprise data — a genuinely different product (AI governance/trust platform) from DQ-of-warehouse-data. Out of scope for DataQ's current mission; noting only so it isn't mistaken for the same category next time this survey is refreshed.
3. **Catalog-as-context-layer-for-third-party-agents (Atlan's MCP framing).** Atlan positions its MCP server less as "authoring DQ checks" and more as "the trust layer any agent should consult before touching data" — a broader governance-platform ambition than DataQ's suite/check/incident model. DataQ's MCP surface is correctly scoped to DataQ's own domain (checks/runs/incidents/assets/lineage) rather than trying to become a universal pre-flight-context provider for unrelated agents — no reason to chase Atlan's broader framing.
4. **Chat-first "ask anything about your data" conversational analyst (Anomalo's AIDA, Soda's chat interface).** Both are closer to a general BI/data-analyst chatbot than a DQ-authoring or RCA tool. This is a materially different product surface (conversational analytics) from DataQ's check-authoring and incident-investigation focus; building it would be scope expansion unrelated to the seams named in the brief (evidence card, monitor kinds, expectation allowlist, profiler, lineage, orchestration, MCP) and isn't validated as necessary by this survey — skip unless a future roadmap explicitly wants a general analyst-chat product.
