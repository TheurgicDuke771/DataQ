### Candidate 1 — psycopg2 `connect_timeout` doesn't bound pooled/reused connections

**Verdict: CONFIRMED**

The mechanics check out against documented behavior, and this doesn't require a live network-partition test to establish — it follows deterministically from how libpq and SQLAlchemy's pool are specified to work:

- **psycopg2/libpq `connect_timeout`** is a libpq connection parameter. It only bounds the time from socket-open through the connection reaching `CONNECTION_OK` (TCP handshake + auth). Once `create_engine()`'s `connect_args` produces a live DBAPI connection and it's returned to the pool, `connect_timeout` has no further effect on that connection — it is not re-applied to reads/writes on an already-open socket, and psycopg2 does not translate it into an ongoing `SO_RCVTIMEO`/socket read timeout.
- **`pool_pre_ping=True`** in SQLAlchemy runs `dialect.do_ping(dbapi_connection)` on checkout — for the psycopg2/postgres dialect this executes a cursor query (effectively `SELECT 1`) on the **existing pooled DBAPI connection object**. This is not a call to `connect()`, so `connect_timeout` is architecturally out of scope for it.
- No `statement_timeout` GUC is set (the file's own comment explicitly says this is deliberate, to not cap legitimate long-running GX queries), and no psycopg2 socket-level keepalive args (`keepalives`, `keepalives_idle`, `keepalives_interval`, `keepalives_count`) are set either — those would be the mechanism that lets the OS detect a silently-dead peer on an idle/in-use socket. Their absence corroborates the gap.
- On a routing-level partition with no RST/ICMP-unreachable, a blocking read on that socket is bounded only by the OS's TCP retransmission timeout (Linux default `tcp_retries2` ≈ 15, commonly 13–30 min depending on RTT) — large and effectively "the same order of unboundedness" the PR set out to eliminate, not the ~10s the fix advertises.

So the reasoning is sound: the fix genuinely narrows the **first-connect** case (a DB that's unreachable *before* the app ever talks to it — cold start, or a connection recycled after `pool_pre_ping` detects and discards a dead one) but does **not** protect a connection that was healthy, is sitting checked-out or idle in the pool, and goes silent mid-life. The file's own comment ("a dead DB fails fast and loudly instead of hanging every caller") overclaims relative to that scope — "every caller" is true only for callers needing a *new* connection, not ones reusing a pooled one. For the specific #1052 staleness-loop shutdown scenario named in the PR, if the partition happens after the loop's connection is already established and pooled, the graceful-shutdown await can still hang for OS-timeout-scale duration.
