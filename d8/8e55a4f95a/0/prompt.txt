## Findings (doc wrong or overclaiming vs code)

**1. `docs/site/guides/ai-features.md:41-42` — "column names and masked aggregate statistics — counts, null rates, min/max, distinct counts — never sample rows" omits that check suggestions send the top-5 most frequent *literal cell values*.**
`backend/app/services/llm_checksuggest.py:207` calls `masked_profile_for_prompt(..., top_n=_TOP_N)` with `_TOP_N = 5`, and lines 217-221 render them:
```python
if col.min_value is not None or col.max_value is not None:
    stats.append(f"range=[{col.min_value}, {col.max_value}]")
if col.top_values:
    top = ", ".join(f"{t.get('value')!r} x{t.get('count')}" for t in col.top_values)
    stats.append(f"top_values=[{top}]")
```
`live_probe.mask_profile_columns` blanks `top_values`/min/max only for columns the EGRESS rung (`run_service._may_show_incidental`, default-mask unless cleared or classifier-non-PII) marks sensitive; every other column's five most frequent raw values (e.g. a free-text `notes`/`comment` column the name/value classifier does not flag) leave the deployment. Failure scenario: an admin reads "never sample rows", enables suggestions on a table with an unclassified free-text column, and its most common cell contents reach a third-party provider. Conversely, SQL generation sends *no* min/max at all (`llm_sqlgen.py` uses `top_n=0` and `_format_profile_lines` emits only `nulls=`/`distinct=`), so the enumeration is inaccurate in both directions. Fix: name "top-N frequent values (masked on sensitive columns)" explicitly and scope min/max/top-values to check suggestions.

**2. `ai-features.md:58-59` — "This card is exactly what the model is handed" is false: the narrative prompt adds a request-time `check_history` layer and a per-requester trim.**
`backend/app/services/llm_rca.py::_evidence_context` does `history = _check_history(session, incident)` → `check_service.list_check_result_history(..., limit=_MAX_HISTORY_POINTS)` with `_MAX_HISTORY_POINTS = 180`, rendered as `check_history (longer trend, oldest→newest, N points)`; it also passes the card through `incident_service.evidence_for_caller` (grant-scoped `same_asset_siblings`). The route docstring (`api/v1/llm.py:257`) itself says "evidence card **+ a longer per-check history**", and the doc's own sample output cites `check_history`. "Nothing is fetched fresh from the *warehouse*" is true, but "exactly what the model is handed" / "describes the failure as it was" is not — the history layer reflects results that landed *after* the incident opened. Fix: "the card plus up to 180 points of the check's result history from DataQ's own database".

**3. `ai-features.md:112-113` — "Once one exists for an incident, the Teams / Slack / email / webhook line for that incident carries its one-line takeaway" overclaims: the narrative is withheld from alerts whenever the asset has any cross-suite sibling check.**

**4. `ai-features.md:41` — "Every feature below sends column names and masked aggregate statistics" is wrong for the RCA narrative, which sends no column names or profile at all.**
