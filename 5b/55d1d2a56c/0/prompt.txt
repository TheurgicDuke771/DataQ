Both call sites collapse to `hmac_secret = _mint_hmac_secret(channel, secret_store)` / `_mint_hmac_secret(channel, secret_store, previous_ref=channel.hmac_secret_ref)`.

## 4. `mint` in `update_channel` conflates "explicit rotate" and "mint on first URL set" into one boolean, losing the distinction for anyone reading or auditing it

**File:** `backend/app/services/channel_service.py`, lines 220–222

```python
mint = regenerate_hmac_secret or (
    channel.webhook_url is not None and channel.hmac_secret_ref is None
)
```

**failure_scenario:** These are two semantically different triggers — one is a user-initiated rotation (`regenerate_hmac_secret=True`), the other is an implicit side effect of setting a URL on a channel that never had a secret. Collapsing them into one `mint` flag means the code that follows (the `apply_secret_webhook` call + `cleared_hmac` cleanup) can't distinguish which case it's in, so if a future requirement needs different behavior per case (e.g. audit-logging "rotated by request" vs. "auto-provisioned on first save" as different `audit_service` actions — the kind of distinction this codebase's audit track already cares about per CLAUDE.md's compliance work), the two cases have to be re-separated from a single flag that already discarded the information. Naming them separately costs nothing:
```python
first_time_mint = channel.webhook_url is not None and channel.hmac_secret_ref is None
mint = regenerate_hmac_secret or first_time_mint
```
— same behavior, but a reader (or a later diff) can see which branch is firing without re-deriving it from the boolean's shape.

## 5. `ChannelRead` threads a write-once plaintext secret through a model that's mostly a read model

**File:** `backend/app/api/v1/notification_channels.py`, lines 27–59

**failure_scenario:** `hmac_secret: str | None = None` is `None` on every one of `ChannelRead`'s five other call sites (`list_channels`, `get_channel`, `list_suite_channels` ×1 each) and is populated only by the two mutation endpoints. That means every list/get response now serializes a `"hmac_secret": null` field that has no meaning outside `create`/`update`, and any future reader of `ChannelRead` has to check the docstring comment ("Populated ONLY by create/rotate") to know the field is dead weight in the five other paths that construct it. A `class ChannelCreateResponse(ChannelRead): hmac_secret: str` (only present when actually populated, and only on the two routes' `response_model`) keeps `ChannelRead` itself a pure read shape and makes "this field only exists after a mint" a type-level fact instead of a comment a caller has to trust. `from_model`'s `hmac_secret` kwarg and the `if hmac_secret is not None` implied contract go away with it.

## 6. `_validate_destination`'s three field-mismatch checks are a copy-pasted triplet that a small table would collapse
