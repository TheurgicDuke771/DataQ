## 3. Findings

### Finding #1 — BLOCKER — FAIL results on a Snowflake/warehouse NUMERIC column crash the entire run, discarding all results

**Repro:** Snowflake suite, single check `expect_column_values_to_be_between` on `subtotal` (NUMERIC) with `min_value=1000000, max_value=2000000` (guaranteed 100% fail). Run status → `failed`, 0/1 checks persisted, no results at all — even though GX successfully computed the metric.

**Root cause (confirmed by direct reproduction inside the api container):**
```
TypeError: Object of type Decimal is not JSON serializable
```
in `sqlalchemy/sql/sqltypes.py` while bulk-inserting the `results` row's JSONB columns. `backend/app/core/jsonsafe.py:24` (`sanitize_json`) explicitly handles numpy scalars, pandas `NA`/`NaT`, dates, and non-finite floats — but has **no branch for `decimal.Decimal`**. When a range check *fails* on a warehouse NUMERIC column, GX's failing-sample/observed-value payload carries the raw `Decimal` values from that column (e.g. the actual `subtotal` amounts), which flow unsanitized into `observed_value`/`sample_failures` via `backend/app/services/run_service.py:113-118` (`_build_result`). A **passing** check on the same column never crashes (the empty failing-list has no Decimal to leak), which is exactly why this was easy to miss in earlier testing.

**Isolation proof (each run individually verified via worker logs):**
- `order_number not null` alone → succeeds (`n_results=1`)
- `subtotal` range **0–100000 (passes)** → succeeds
- `subtotal` range **1000000–2000000 (fails)** → crashes with the exact Decimal TypeError, reproduced twice independently (once inside the original 4-check batch, once alone)
- `channel` in-set FAIL (string column) → succeeds normally, confirming the bug is Decimal-specific, not FAIL-status-generic

**Impact:** Any Snowflake or Unity-Catalog suite with a range/threshold check on a currency, quantity, or other NUMERIC column that legitimately fails will silently lose the entire run's results — precisely the "the check actually caught something" scenario a DQ platform exists to preserve. Not matched by any open GitHub issue (`gh issue list` searched for "Decimal", empty). **This must block the prod deploy.**

**Fix direction:** add a `decimal.Decimal` branch to `sanitize_json` (e.g. `if isinstance(value, decimal.Decimal): return float(value)`), mirroring the existing numpy/pandas coercion pattern.

### Finding #2 — BLOCKER (scoped to Iceberg+S3-compatible storage) — pyiceberg's PyArrow S3 FileIO gets `ACCESS_DENIED` reading table metadata from MinIO; "Test Connection" doesn't catch it

**Repro:** Iceberg connection (Test Connection: ✅ Connected) → any column-listing call or check dry-run against `retail.purchase_orders` → 502 `profile_failed` / `dry_run_failed`.

**Root cause (confirmed by direct reproduction inside the api container, `load_iceberg_table` in `backend/app/datasources/iceberg.py:222-241`):**
```
OSError: When reading information for key 'warehouse/retail/purchase_orders/metadata/00006-....metadata.json'
in bucket 'iceberg': AWS Error ACCESS_DENIED during HeadObject operation: No response body.
```
This happens inside `pyiceberg.io.pyarrow`'s `PyArrowFileIO`, using the exact same `s3.access-key-id`/`s3.secret-access-key`/`s3.endpoint`/`s3.path-style-access` properties that the connection's boto3-based Test Connection accepted and that the sibling AWS S3 connection type (boto3-based) successfully authenticates with against the same MinIO instance/credentials. Test Connection only verifies catalog reachability (a lightweight Postgres query via the SQL catalog backend) — it never actually reads a table's metadata file from S3, so this failure is invisible until a user tries to run a real check.

**Impact:** blocks 100% of check execution for any Iceberg connection backed by an S3-compatible (non-AWS) store — the exact configuration this task specified. Not matched by any open issue (`gh issue list --search iceberg` returned only #717/#327/#595/#597/#1118/#1270, none about S3 FileIO auth).

**Fix direction:** compare pyarrow's S3FileSystem property expectations against what boto3 accepts — likely needs an explicit `s3.region` (pyarrow's S3FileSystem sometimes requires a region even against non-AWS endpoints) or a different property name for forcing path-style addressing in PyArrow's own S3 client vs. boto3's `addressing_style`. Worth a live-network debug session with `pyarrow.fs.S3FileSystem` directly against MinIO.
