  I recommend `python-tds` + `sqlalchemy-pytds` as the MSSQL driver, but only if a live spike passes first. ADR 0044 is drafted as **Proposed** in docs-only PR https://github.com/TheurgicDuke771/DataQ/pull/2121 (branch `docs/adr-mssql-driver`, milestone v1.2 Backlog, `Refs #1679`, not merged). Findings comments are posted on #1679 and #1680. No Azure resource, role assignment or app registration was created or changed; every Azure/Graph query was a read.
  
  **Recommendation and rationale (#1679).** Every Microsoft Python path to SQL Server depends on the proprietary ODBC Driver 18 binaries:
  - **`pyodbc` + msodbcsql18:** I read the actual EULA text. It lets you redistribute only code on a REDIST list, and I could not find one naming the Linux package. It requires anyone who redistributes it to make downstream users agree to Microsoft-protective terms (§2(b)(ii)) and to indemnify Microsoft (§2(b)(iii)). That can't go into the MIT GHCR image without a rule-40 exception, and it would also add apt packages back to the runtime image.
  - **`mssql-python`:** MIT itself, but it hard-depends on `mssql-python-odbc`, which PyPI classifies as Other/Proprietary and which carries the same binaries. It also needs apt packages (`libltdl7 libkrb5-3 libgssapi-krb5-2`), and its SQLAlchemy dialect exists only in SQLAlchemy 2.1; we pin 2.0.54.
  - **`pymssql`:** LGPL is acceptable, but FreeTDS cannot send an Entra token (the upstream request has been open since 2023). Fabric accepts only Entra identities, so pymssql cannot reach it at all.
  - **`python-tds` + `sqlalchemy-pytds`:** both MIT and pure Python, about 95 KB of wheels, no apt, trivially multi-arch. I confirmed in the source that `access_token_callable` sends the Entra token over TDS (FEDAUTH) and that TDS routing is implemented. The dialect subclasses SQLAlchemy's `MSDialect`, so GX sees it as `mssql` through its generic `add_sql`. GX's own `add_sql_server` / `add_fabric` hardcode `mssql+pyodbc`, so we can't use those builders.
  - **Risks the ADR guards against:**
    - Each package has one maintainer; `sqlalchemy-pytds` is Beta, last released 2024-09, and small enough to vendor.
    - TLS is only turned on when a CA bundle (`cafile`) is passed.
    - Hostname checking is hand-rolled and uses an `lstrip('DNS:')` that can wrongly reject valid names.
    - TLS 1.2 only, with no TDS 8 strict mode.
  - **Spike pass criteria:**
    - Azure SQL with a SQL login and with a service-principal token.
    - A Fabric Warehouse and a Lakehouse SQL endpoint.
    - Azure SQL's Redirect connection policy.
    - GX checks running through `mssql+pytds`.
    - A wrong hostname and an untrusted certificate authority both being refused.
  - **Fallback:** if the spike fails, use `pyodbc` + msodbcsql18 under a separate exception ADR with counsel sign-off.
  
  **Auth design.**
  - One engine-generic `mssql` connection type with two modes:
    - `sql`: username in config, password as the secret.
    - `entra_service_principal`: `tenant_id` and `client_id` in config, client secret as the secret. This is the same shape as the ADF connection, so nothing new in the secret store.
  - Tokens come from `azure-identity`'s `ClientSecretCredential` (already a dependency) for scope `https://database.windows.net/.default`. The adapter fetches a token for each new physical connection; `azure-identity` caches and refreshes it, so there is no refresh code of our own. Engines are built per run.
  - Changing `host`, `port`, `tenant_id` or `auth_type` requires re-supplying the secret, the same rule the other adapters use to stop a stored credential being redirected.
  - Deferred: managed identity, certificate credentials, sovereign clouds.
  - The customer must enable the Fabric tenant setting "Service principals can use Fabric APIs" and give the service principal a workspace role.
