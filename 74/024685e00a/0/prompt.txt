## What the bug actually was (verified against installed GX 1.17.2, not from memory)

The issue's framing ("COMPLETE materialises the full unexpected-index list") is half right, and the half it got wrong is the interesting half:

- `_sqlalchemy_map_condition_index` (the **locator** query) **already** `.limit(result_format["partial_unexpected_count"])`, which defaults to 20 = our `SAMPLE_ROW_CAP`. So locators were never the unbounded fetch.
- `_sqlalchemy_column_map_condition_values` (the unexpected **values** query) puts its `LIMIT` inside the `!= COMPLETE` branch — so under COMPLETE it emits `SELECT col AS unexpected_values FROM … WHERE &lt;fail cond&gt;` **with no LIMIT at all**. Client-side materialisation is capped by `fetchmany(MAX_RESULT_RECORDS=200)`, so the real exposure is warehouse-side result-set materialisation + the streamed fetch (and the worker too on drivers that buffer whole result sets). That is the live defect on Snowflake and UC pushdown.

Proven by running real GX on a sqlite SQLAlchemy batch and spying on emitted SQL — the values query came back LIMIT-less at 500 failing rows.

## Fix

SQL lanes now request `SUMMARY` with `partial_unexpected_count = min(SAMPLE_ROW_CAP, MAX_RESULT_RECORDS)`, which puts the same `LIMIT` on **both** row-returning queries; `SUMMARY` returns the identical locator rows under `partial_unexpected_index_list`, so `_extract_sample_failures` reads either key and still writes our stable `unexpected_index_list`. Lane detection is `isinstance(batch_definition.data_asset.datasource, SQLDatasource)` (Snowflake + Databricks-SQL both subclass it), so **frame lanes keep COMPLETE byte-identically**. Byte-compat proven by diffing the mapped `SuiteOutcome` from both formats: **identical** at 3, 20 and 200 failing rows across map/aggregate/distinct-value expectations.

Sibling fields checked: `partial_unexpected_list` inherits the bound; `unexpected_list`/`unexpected_index_query`/custom SQL's `details.unexpected_rows` are COMPLETE-only and read by nothing in DataQ; distinct-values `observed_value` is result-format-insensitive and already SQL-limited (#1229 class not left open). Residuals recorded in `docs/site/architecture/perf-baseline.md`.
