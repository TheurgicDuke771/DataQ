## 1. Monitor-kind implementation: dispatch, shapes, metric_value/duration_ms/status

**Core engine:** `backend/app/datasources/monitors.py`

- Kind constants: `FRESHNESS = "freshness"` (line 45), `VOLUME = "volume"` (46), `SCHEMA_DRIFT = "schema_drift"` (47).
- **Registry pattern (#726)** — the dispatch mechanism, not an if-chain:
  - `MonitorKindStrategy` dataclass (~line 400): `kind`, `validate_config: Callable[[dict], None]`, `outcome: Callable[[scalar, config, now], CheckOutcome]`, `build_statement: Callable[[TableClause, config], Select] | None`.
  - `MONITOR_KIND_REGISTRY: dict[str, MonitorKindStrategy]` (dict literal, import-time only) — freshness/volume have a `build_statement`; `schema_drift` has `build_statement=None` (routes it to the stateful path instead of the scalar SQL path).
  - Derived tuples (also import-time, never mutated): `MONITOR_KINDS`, `SCALAR_MONITOR_KINDS` (kinds with `build_statement is not None`), `STATEFUL_MONITOR_KINDS` (kinds with `build_statement is None`).
- **Evaluation-function shape**:
  - `validate_config(kind, config) -&gt; None` — raises `MonitorConfigError` (DB-free structural gate, used both at authoring time and defensively at run time).
  - `build_monitor_statement(kind, *, table, schema, catalog, config) -&gt; Select[Any]` — SQLAlchemy Core statement (never a raw SQL string, per #476 identifier-quoting discipline); raises if the kind has no scalar-SQL form.
  - `monitor_outcome(kind, *, scalar, config, now) -&gt; CheckOutcome` — turns the scalar aggregate result into `CheckOutcome` (`backend/app/datasources/base.py`), which carries `expectation_type`, `success`, `metric_value: float | None`, `observed_value`, `expected_value`, `sample_failures`, `errored`, `error_message`.
- **`monitor_expectation_type(kind) -&gt; str`** — canonical `"monitor:&lt;kind&gt;"` string, single source of truth shared by run path, authoring, and frontend catalog.
- **Per-kind functions** (the freshness/volume "reference shape" a new `anomaly` strategy should mirror):
  - `freshness_column`, `_validate_freshness`, `_freshness_statement`, `_freshness_outcome` — metric = age in hours (`_freshness_age_hours`), higher = worse.
  - `_volume_bounds`, `_validate_volume`, `_volume_statement`, `_volume_outcome` — metric = % deviation outside `[min_rows, max_rows]` (`_volume_deviation_pct`), higher = worse.
  - `_validate_schema_drift`, `_schema_drift_outcome` — metric = drifted-column count (float), scalar is a **dict payload** (not a SQL scalar) computed by the stateful executor.
- **Run-time execution helpers**:
  - `run_monitor_specs(scalar_for, *, monitors, now)` — bands a list of `MonitorSpec`s given a scalar source; isolates a bad monitor to its own `errored` outcome (never fails siblings); routes exceptions through `classify_failure_reason` unless the exception is a `SafeMonitorError` subclass (persisted verbatim — see the `SafeMonitorError`/`MonitorConfigError` docstrings, ~lines 60-115, on what's safe to persist into `results.observed_value`/message given #900/#828/#989).
  - `evaluate_monitors(fetch_scalar, *, table, schema, catalog, monitors)` — SQL-scalar path, builds the statement then calls `fetch_scalar`.
  - `run_monitors_over_engine(engine, *, table, schema, catalog, monitors)` — the shared execution edge SQL runners (Snowflake, Unity Catalog) use: opens one connection, sources every monitor's scalar from it (#428).

**Dispatch by `check.kind` (ADR 0012 seam):** `backend/app/services/run_service.py`, function `_run_outcomes` (lines 115-226):
- `expectation_idx` → GX `CheckRunner.run_checks` (existing GX path).
- `monitor_idx = [... c.kind in SCALAR_MONITOR_KINDS]` → runner's `run_monitors` (gated by the runner's advertised `supported_monitor_kinds` capability set, line 198 — **not** `isinstance`, to avoid a Protocol name-match footgun).
- `stateful_idx = [... c.kind in STATEFUL_MONITOR_KINDS]` → the injected `stateful_monitor_executor: Callable[[Check], CheckOutcome] | None` (built by the worker per-run, owns the DB session/baseline store — runners never see it). No executor supplied → per-check `errored` outcome (line 156-165), never a hard failure.
- `comparison_idx` → injected `comparison_executor` (ADR 0015 pattern, same no-executor semantics).
- Any kind not in `{expectation, *MONITOR_KINDS, comparison}` → `NotImplementedError` (line 152) — this is why `anomaly` is currently unreachable at run time even though it's schema-valid.
- `anomaly` (stateful shape, needing a stored baseline like `schema_drift`) would join `STATEFUL_MONITOR_KINDS` by registering with `build_statement=None`, and needs its own `build_anomaly_executor`-style injection wired the same way `schema_drift` is (see §2/§7 below, `backend/app/worker/tasks.py:198-210`).

**`metric_value` / `duration_ms` / status production**:
- `metric_value`: For monitors, `CheckOutcome.metric_value` is set directly by the strategy's `outcome()` function (`backend/app/datasources/base.py` ~line 60, doc comment: "the badness scalar a monitor computed directly ... higher = worse"). For GX expectations, `severity.extract_metric` (see §3) pulls `unexpected_percent` from `sample_failures` instead. `severity.extract_metric` prefers `outcome.metric_value` when set (`backend/app/services/severity.py` lines ~30-63).
- `duration_ms`: stays `NULL` in v1 — `backend/app/services/run_service.py:69` comment ("per-check timing isn't separable from GX's single suite-level `validate()`") and ADR 0012 (`docs/adr/0012-monitor-kind-seam.md` line 93, ADR 0016 line 31). Not computed per-monitor at all currently — a new kind gets the same `NULL`.
- Status: produced by `severity.resolve_status`/`derive_status` (see §3) inside `run_service._build_result` (`backend/app/services/run_service.py:64-109`), which maps a `CheckOutcome` + the check's three thresholds to a `Result` row (`status`, `metric_value`, `observed_value`, `expected_value`, `sample_failures`).

## 2. `schema_drift` (#592) baseline persistence shape (PR #876) — the shape #593 (`anomaly`) must reuse

**Model:** `MonitorBaseline` in `backend/app/db/models.py:530-569`, table `monitor_baselines`.

Columns:
- `id` (UUID PK)
- `check_id` — FK `checks.id`, `ondelete="CASCADE"`, not null
- `kind` — `String(32)`, not null, **denormalized** from the check for queryability; check's own `kind` is the authority
- `baseline` — `JSONB`, not null — **kind-shaped payload**; `schema_drift` stores `{"columns": [{"name": ..., "type": ...}, ...]}`. `anomaly` (#593) is explicitly documented (line 536) to reuse this exact shape for its "metric-baseline parameters" JSONB
- `captured_at` — `DateTime(timezone=True)`, server_default `now()`
- `captured_by` — nullable FK `users.id`, `ondelete="SET NULL"`; NULL = run path captured it automatically (first run); non-NULL = manual re-baseline actor
- `created_at`, `updated_at` (standard)

Constraints (`__table_args__`, lines 548-551):
- `UniqueConstraint("check_id", name="uq_monitor_baselines_check")` — **one CURRENT baseline per check**; a re-baseline REPLACES the row (no history kept here — history lives in `results`).
- `_in_check("kind", CHECK_KINDS, "kind_valid")` — CHECK constraint against the shared `CHECK_KINDS` vocabulary (which already admits `"anomaly"`).

**Migration:** `backend/app/alembic/versions/e2f3a4b5c6d7_add_monitor_baselines.py` — creates the table exactly as above, with a **frozen copy** of `CHECK_KINDS` (line 40: `_CHECK_KINDS = ("expectation", "freshness", "volume", "schema_drift", "anomaly", "comparison")` — migrations never import live app code). Its docstring literally states: "Designed for TWO consumers: ... the W5 `anomaly` kind (#593) stores its metric baseline parameters in the same shape, so the payload is a kind-shaped JSONB — one persistence shape, no second table later." **This confirms no new migration is needed for `anomaly`'s baseline storage** — only a differently-shaped JSONB payload under the same table/columns.

**Read/write/re-baseline logic:** `backend/app/services/schema_drift.py`
- `get_baseline(session, check_id) -&gt; MonitorBaseline | None` (select by `check_id`).
- `rebaseline(session, check) -&gt; bool` — **deletes** the row (not an immediate recapture — avoids running introspection on the API request thread); next run recaptures live. Returns whether a row existed.
- `build_schema_drift_executor(session, *, connection, target_table, target_schema, target_catalog, secret_store, persist=True) -&gt; Callable[[Check], CheckOutcome]` — the per-run closure pattern:
  - No baseline row → captures current snapshot, `INSERT ... ON CONFLICT DO NOTHING (constraint="uq_monitor_baselines_check")` (handles concurrent first-runs racing on READ COMMITTED without blowing up the whole run's commit), reports "baseline captured" (`success=True`, `metric_value=0.0`).
  - Baseline row exists → diff current vs stored (`diff_schemas`), band via `monitor_outcome(SCHEMA_DRIFT, scalar=payload, config=config, now=...)`.
  - `persist=False` → dry-run mode: nothing written, missing baseline previews as "would capture."
  - Introspection failure → the **check's** operational error, not the run's (one unreachable target doesn't fail siblings).

**Wiring (worker):** `backend/app/worker/tasks.py:198-210` — builds `stateful_monitor_executor` only when `any(c.kind in STATEFUL_MONITOR_KINDS for c in checks)`, then passes it into `run_service.execute_run(..., stateful_monitor_executor=...)`. An `anomaly` executor (`build_anomaly_executor`) would be built the same way, gated on `STATEFUL_MONITOR_KINDS` membership (which is automatic once registered with `build_statement=None`), and `run_service._run_outcomes` would need it threaded through similarly (it currently only accepts one `stateful_monitor_executor` param serving *all* stateful kinds via `STATEFUL_MONITOR_KINDS`, so both `schema_drift` and `anomaly` executors need to be composed/dispatched — check how `_run_outcomes` calls a single `stateful_monitor_executor(checks[i])` for every stateful-kind index, line 155-167 — the executor closure itself would need to branch on `check.kind` internally, or the signature needs to grow a second executor param, mirroring how `comparison_executor` is a separate param from `stateful_monitor_executor`).

## 3. ADR 0016 severity thresholds → status banding

**Where thresholds live:** columns on `Check` (`backend/app/db/models.py:513-515`): `warn_threshold`, `fail_threshold`, `critical_threshold` — all `Mapped[Decimal | None] = mapped_column(Numeric)`. NOT JSONB — plain nullable NUMERIC columns, one check = up to 3 thresholds, kind-agnostic (any kind can set them). Mirrored on `CheckVersion` (lines 611-613) for history snapshots.

**Banding code:** `backend/app/services/severity.py` (ADR 0016, "approach A"):
- `extract_metric(outcome: CheckOutcome) -&gt; Decimal | None` — prefers `outcome.metric_value` (monitor kinds set this directly); else falls back to GX's `unexpected_percent` from `sample_failures`. Uses `Decimal(str(raw))` for exactness; treats non-finite (`NaN`/`inf`) as "no metric."
- `derive_status(*, success, metric_value, warn_threshold, fail_threshold, critical_threshold) -&gt; str` — the pure banding function: `metric_value &gt;= critical_threshold → "critical"`, else `&gt;= fail_threshold → "fail"`, else `&gt;= warn_threshold → "warn"`, else `"pass"`; unset thresholds treated as `+∞`; no thresholds or no metric → binary `pass`/`fail` from `success`.
- `resolve_status(outcome, *, warn_threshold, fail_threshold, critical_threshold) -&gt; tuple[status, metric]` — the single entry point both `run_service._build_result` and `dryrun_service` call, so a dry-run preview can never disagree with what a real run would persist. `outcome.errored=True` short-circuits to `("error", None)` — no tier, no metric.

For `anomaly`, the same thresholds field reuse applies: whatever scalar the anomaly strategy's `outcome()` sets as `CheckOutcome.metric_value` (e.g. a z-score, or a deviation-from-baseline percent — "higher = worse" per the repo's stated convention) gets banded by the *same* generic `derive_status`, no new severity code needed — this is explicitly the ADR 0016 design ("the model generalizes to v1.x freshness/volume monitors ... also 'higher = worse' scalars," `docs/adr/0016-severity-derivation-semantics.md:39`).

## 5. `skip` status path (#297/#298)

`RESULT_OPERATIONAL_STATUSES = ("skip", "error")` (`backend/app/db/models.py:48`) — orthogonal to the four severity tiers (`pass/warn/fail/critical`), excluded from health-score N, no penalty weight.

`skip` is a **run-level**, not a per-monitor, concept in this codebase: it means "the whole run had nothing to evaluate" (e.g., a flat-file batch hasn't landed yet), not "this one monitor kind decided to skip itself." Persistence: `backend/app/services/run_service.py:332-354`, `skip_run(session, *, run, checks, reason) -&gt; Run` — sets `run.status = "running"` → commits every check a `Result(status="skip", observed_value={"reason": reason})` → `run.status = "succeeded"`. The run still succeeds; only its results are all `skip`.

Called from exactly one place: `backend/app/worker/tasks.py:165` — `run_service.skip_run(session, run=run, checks=checks, reason="batch_not_found")` (flat-file batch resolution failure).

Rendering: `backend/app/services/run_service.py:426-447` computes per-run `(has_error, has_skip)` flags over "operational" statuses for run-list badges; `worst_severity()` (line 65-74) explicitly never ranks `pass`/`skip`/`error`.

For `anomaly`, if a per-check "not enough baseline history yet" case should map to `skip` rather than `pass`/`error`, note that today `skip` is only produced at the whole-run granularity via `skip_run`, never per-check inside `_build_result`/`CheckOutcome`. A per-check anomaly "insufficient history" case would need either (a) a new `errored=False`/special outcome path that `_build_result` maps to `skip` per-check (not currently supported — `_build_result` only derives `error` from `outcome.errored` and the four tiers from `resolve_status`), or (b) treat it as the schema_drift precedent does for "first run" — a passing "baseline captured" result rather than a skip. Tests referencing skip: `backend/tests/integration/test_datasource_runs.py:218`, `backend/tests/services/test_run_service.py:541`, `backend/tests/worker/test_tasks.py:312`, `backend/tests/api/test_runs.py:386-389`.
