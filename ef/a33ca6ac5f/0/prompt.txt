### 4. SecretStore seam
- **Interface:** `backend/app/core/secrets.py`, `@runtime_checkable class SecretStore(Protocol)` (line 107): `get(name) -&gt; str`, `set(name, value) -&gt; None`, `delete(name) -&gt; None` (best-effort/fail-soft). Impls: `EnvSecretStore`, `AzureKeyVaultStore`, `AwsSecretsManagerStore`, `OpenBaoSecretStore` (ADR 0039). Factory `_build_store(settings)` (line 727) / singleton `get_secret_store()` (line 762).
- **Connection naming:** `backend/app/core/secret_names.py`, `connection_secret_ref(*, connection_id, env, name, conn_type="", kind="") -&gt; str` (line 80) — builds `conn-&lt;type&gt;-&lt;qualifier&gt;-[&lt;kind&gt;-]&lt;env&gt;-&lt;shortid&gt;`, charset-constrained to Key Vault's `[0-9a-zA-Z-]`, ≤127 chars via `_MAX_SLUG=60` + 8-hex-char id. `kind` param exists precisely for "a second credential on the same row" (e.g. Iceberg REST catalog secret).
- **How a NEW kind of secret would be namespaced** — two existing precedents:
  1. **Fixed, workspace-wide capability secret** (like a signing key/PAT): a static **Settings field naming the KV key**, e.g. `backend/app/core/config.py` lines 237-250: `adf_webhook_secret_name: str = "adf-webhook-secret"`, `teams_webhook_secret_name`, `slack_webhook_secret_name` — one secret per install, admin sets the value via the vault directly; the app only stores/reads the **name**, never the value, in `Settings`. Read via `admin_service._safe_secret(secret_store, secret_name)` (`admin_service.py` line 261).
  2. **Per-entity, DB-referenced secret** (like a per-suite webhook URL): `notification_service._apply_secret_webhook(...)` (line 129-144) mints `ref = current_ref or f"{ref_prefix}-{config_id}-{uuid.uuid4().hex[:12]}"`, stores the value via `secret_store.set(ref, value)`, and persists only the **ref** in a DB column (`SuiteNotification.webhook_secret_ref`). This is the simpler sibling of `connection_secret_ref` for non-connection secrets.
  - For an LLM provider credential (workspace-admin, single credential per install, per the design doc below), pattern (1) or a `llm_provider_secret_ref` DB column + pattern (2)-style mint-on-set is the natural fit — precedent exists both ways.

## Key finding: the design is already drafted

`docs/post-v1-dq-intelligence-notes.md` (Status: filed as GitHub issues #1509-#1513, **#1511 is literally "the LLMProvider seam"**) already specifies almost exactly what you're designing:
- Workspace-admin-configured (ADR 0033 `role='admin'`), **default-OFF**, **BYOL** (customer's own credential/endpoint, never proxied through a DataQ-owned key).
- Pluggable impls: Anthropic API (default), Azure AI Foundry/Azure OpenAI, AWS Bedrock, any OpenAI-compatible endpoint (the "local LLM" answer via Ollama/vLLM/TGI — explicitly **not** bundling a model server, citing ADR 0025 slim-image).
- Credential stored in `SecretStore`; seam shape `{base_url, api_key, model, auth_adapter}` + a capability flag for structured-output support.
- Runs in the **Celery worker**, not the request path (already holds secret access; async).
- Data-residency discipline: send **schema + aggregate profiler stats only, never raw sample rows / PII-column values** — reuse the redaction seam (`live_probe`, `column_classification`, `derive_column_policy`).
- #2 (SQL generator) and #3 (check suggestions) both **must** route generated output through the *existing* ADR-0019 custom-SQL validator + dry-run and the (new, #1510) `expectation_allowlist.py`, respectively — "trust LLM output no more than user input."
- `admin.py`'s `DeploymentPostureRead.external_transfers` already carries a placeholder `llm_intelligence` entry (line 404-417) marked `enabled=False`, explicitly flagged "listed while disabled on purpose: an auditor should see it was considered" — this will need to flip to `enabled=True`-when-configured once the seam lands, and should read the new admin config to compute that.
