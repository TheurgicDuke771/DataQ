  ## 🟡 Concerns
  
  1. **`op.create_check_constraint(...)` without `NOT VALID` — full-table ACCESS EXCLUSIVE scan on `suites`, `checks`, `incidents`** (lines 41-43, 55-57, 65-69).
     PostgreSQL's fast-default optimization (PG 11+) means `ADD COLUMN ... server_default` doesn't rewrite the table — the migration's docstring is correct about that. But `ADD CONSTRAINT CHECK (...)` without `NOT VALID` still requires PostgreSQL to visit every existing row to validate the new constraint, and it holds an **ACCESS EXCLUSIVE lock for the whole scan** (blocks all reads and writes on that table, not just writers). Because every pre-existing row already satisfies the new constraints trivially (fresh default-backed `origin`, `NULL` `resolution`), the scan can't fail — this is purely a *lock-duration* risk, not a correctness one. `suites`/`checks`/`incidents` are metadata tables (one row per authored object, not per execution) rather than the `runs`/`results`/`pipeline_runs` scale CLAUDE.md calls out, so the actual blast radius today is probably small — but this is exactly the shape the working agreement's "Acceptable patterns" section calls out (`NOT VALID` → later `VALIDATE CONSTRAINT`), and per-cloud these tables will keep growing with the coverage-loop feature itself (more auto-created checks/suites). Recommend splitting to `op.create_check_constraint(..., postgresql_not_valid=True)` (i.e., append `NOT VALID` — Alembic doesn't have a `postgresql_not_valid` kwarg; use `op.execute("ALTER TABLE ... ADD CONSTRAINT ... CHECK (...) NOT VALID")`) followed by a separate `op.execute("ALTER TABLE ... VALIDATE CONSTRAINT ...")` — either in a later migration or in the same file but outside the single ACCESS EXCLUSIVE window (VALIDATE CONSTRAINT only needs SHARE UPDATE EXCLUSIVE). Verify against whoever owns the deploy whether these tables are big enough today to justify the extra migration, or whether it's cheap insurance for the future.
  
  2. **`op.create_index("uq_suites_auto_per_asset", ...)` without `postgresql_concurrently=True`** (lines 44-50).
     Same ACCESS EXCLUSIVE-for-the-scan-duration issue as above, this time on `suites` specifically — the table the checklist explicitly asked about. Even though it's a partial index (`WHERE origin = 'auto'`) that will end up empty at creation time (no row has `origin='auto'` yet since the column doesn't exist until this same migration), PostgreSQL still has to scan the whole table's heap to evaluate the predicate row-by-row before it can conclude the index is empty — so build time scales with `suites` table size, not with matching-row count. Recommend `postgresql_concurrently=True` in its own migration, run via `with op.get_context().autocommit_block():` since `CREATE INDEX CONCURRENTLY` cannot run inside Alembic's default transactional-DDL wrapper (this repo's own alembic history has hit that exact `transactional_ddl = False` no-op gotcha before). Given `suites` is read on essentially every dashboard/suite-list/run-trigger request, a lock here — however brief today — is worth avoiding as the table grows.
