## Alerts and dialogs

IMPORTANT: Do not trigger JavaScript alerts, confirms, prompts, or browser modal dialogs through your actions. These browser dialogs block all further browser events and will prevent the extension from receiving any subsequent commands. Instead, when possible, use console.log for debugging and then use the mcp__claude-in-chrome__read_console_messages tool to read those log messages. If a page has dialog-triggering elements:
1. Avoid clicking buttons or links that may trigger alerts (e.g., "Delete" buttons with confirmation dialogs)
2. If you must interact with such elements, warn the user first that this may interrupt the session
3. Use mcp__claude-in-chrome__javascript_tool to check for and dismiss any existing dialogs before proceeding

- Unexpected complexity or tangential browser exploration
- Browser tool calls failing or returning errors after 2-3 attempts
- No response from the browser extension
- Page elements not responding to clicks or input
- Pages not loading or timing out
- Unable to complete the browser task despite multiple approaches

Explain what you attempted, what went wrong, and ask how the user would like to proceed. Do not keep retrying the same failing browser action or explore unrelated pages without checking in first.

  ## Recommended design
  
  Amend ADR 0047 instead of writing a new ADR. The amendment would (a) record that #1661's "first-class per-asset system" is the automatic suite, (b) add a sensitivity hierarchy, and (c) partly reverse the rejected "Coverage per asset or workspace-wide" line, for sensitivity only and not for the opt-in.

The effective values are resolved when the suite runs. Existing automatic checks carry explicit 3/4/6; they can be treated as inheriting when they are `origin='auto'` with a single `check_versions` row (never edited), or left alone. I did not trace where thresholds are banded (`backend/app/services/severity.py` and the runner); that seam needs a look before sizing S2 firmly.
  - **Apply at creation only.** Simpler, but a workspace change never reaches existing suites, which defeats "not per-check".

  ## Can the secret ref move without reading the value?
  
  Yes. The ref is a pointer string. In one transaction, set `channel.webhook_secret_ref = suite_notification.webhook_secret_ref` and set the suite column to NULL. No `secret_store.get` or `set` is needed.
  
  Constraints I verified:
  - **Do not use the existing clear path.** `upsert_config(webhook="")` deletes the cleared ref from the store after commit (`notification_service.py:313-315`), which would destroy the secret the channel now owns. The promote path needs its own null-out with no `secret_store.delete`.
  - **The sweep stays correct.** The moved ref keeps its `suite-notif-…` name, still matches `_DATAQ_PREFIXES`, and is owned through `NotificationChannel.webhook_secret_ref`. Later channel rotations reuse it.
  - **No re-validation is possible without reading the URL**, but the publishers re-check the allowlist at send time (`teams.py:66`, `slack.py:201`).
  - **Email is not a secret**: copy `email_recipients` into an `email` channel.
  - **It should be Admin-gated.** It creates a workspace-visible channel holding a credential, and channel mutations are `AdminUser`. A suite editor cannot promote.
  
  ## What happens to the legacy field
  
  **Clear (move the ref).** One owner for the secret; rotation touches one place.
  - Trap: with the legacy field NULL, `primary` falls back to the **workspace default**. If `TEAMS_WEBHOOK_SECRET_NAME`, `SLACK_WEBHOOK_SECRET_NAME` or `EMAIL_TO` is set, the suite starts alerting the workspace destination as well as the channel.
  - This is extra delivery to a second destination, not a duplicate to the same one. It is unavoidable under the current resolver, and it already happens today whenever someone clicks Clear after linking a channel.
  - The endpoint can detect it without reading secrets (whether the settings name is non-empty, as `get_notification_config` does) and the UI can warn.
  
  **Keep, sharing the ref.** Behaviour is identical at first (same URL, deduped, workspace default still suppressed). Hazards:
  - A later Clear, or `delete_config`, deletes the secret from under the channel and breaks every suite linked to it.
  - Deleting the channel deletes the secret from under the legacy field.
  
  Two columns owning one secret is the trap the sweep comments warn about.
  
  **Keep, copying the value to a new ref.** Needs a server-side `get` and `set` (the value never leaves the process). Deduped until the channel is rotated; after that the suite alerts both the old and new URL. This is the real double-delivery risk, and it defeats the rotation acceptance test.
  
  ## Recommendation: guided in-app action, move and clear
  
  Against an automatic data migration:
  - It cannot dedupe without reading secrets, so 8 suites sharing one URL become 8 single-suite channels, the opposite of "rotation touches one place".
  - It cannot name channels meaningfully.
  - It has no audit actor.
  - It would trigger the workspace-default fallback for every affected suite at deploy, silently.
  - It is hard to roll back.
  
  The guided action is explicit, audited and per suite, and needs **no migration**.
  
  Suggested shape: `POST /suites/{suite_id}/notifications/promote`, with body `{field: "teams"|"slack"|"email", name}`, `AdminUser`. In one transaction: create the channel with the moved ref (or copied recipients), link it to the suite, null the legacy field. Return the channel plus a flag saying the workspace default now applies.
  
  Open design choice: for a second suite holding the same URL, the admin links the existing channel and clears; promoting again would create a duplicate channel.

  ## (a) Recommended minimal design for the persisted source
  
  **Storage**
  - Add two nullable columns on `assets`, mirroring the G3 pair: `detected_classifications JSONB` and `detected_classifications_at timestamptz`.
  - Shape: `{column_lower: {"verdict": "sensitive", "detector": "email"|"encoded"|"name", "summary": {n, email_count, id_shaped_count, encoded_count, distinct_count}}}`.
  - Store counts only, never values. Reuse `value_signal_summary` / `_valid_summary`.
  - Write even when empty, with the timestamp, so "looked and found none" differs from "never looked".
  - Keep it out of `column_tags`, for the four reasons above: `refresh_asset_column_tags` overwrites it each run; its keys suppress lineage inheritance; `inherited_sensitive` would propagate a heuristic downstream as warehouse truth; a `public` value would clear in fail-closed mode.
  
  **Writers** (all worker-side, all `machine_write`, all no-ops without `suite.asset_id`)
  1. `_auto_classify_columns` (`backend/app/worker/tasks.py:352`): split `derive_column_policy` so it also returns per-column affirmative verdicts via `is_sensitive`, not `classify_column`, whose default is PII.
  2. `suggestion_service.refresh_from_profile` (`:181`), which already profiles auto-coverage tables.
  3. The `pii_drift` executor on each run.
  
  **Readers**
  - Zero call-site churn: add one helper `_detected_sensitive(column, detected)` and OR it into the `is_sensitive` rung of `_known_sensitive`, `_may_show_incidental` and `value_signal_decides`.
  - Deliver the map through the one choke point every surface already uses (`effective_column_tags` / `run_service.asset_column_tags`), either as a second return value or a small `Classifications` object.
  - Position in the ladder: warehouse tag (plus lineage), then `pii_columns`, then fail-closed, then persisted profiler verdict, then live name/value heuristic, then default mask.
  - Make it additive-only. Persist only `sensitive`; a persisted verdict must never clear a column and never satisfy fail-closed clearance. Keep the live name heuristic as the fallback for unprofiled assets.
  
  **Decisions that need an ADR (or an amendment to the G3 docs / ADR 0034)**
  1. **Can a suite's `identifier_column` override a profiler verdict?** If the verdict is merged as a hard tag floor it cannot be lifted, and on Postgres, MySQL, files and Iceberg there is no warehouse tag to clear a false positive (hash-like or base64 IDs can trip `encoded`). Placing it at the heuristic rung, as recommended, already blocks `identifier_column` because `is_sensitive` beats it; this needs to be explicit.
  2. **JSONB on `assets` versus a normalized `asset_column_classifications(asset_id, column, source, verdict, …)` table.** The table suits the future governance-catalog source and SQL queries. JSONB matches the G3 precedent and is the minimal option.
  3. **Staleness.** A verdict outlives the data; that is safe only because it is additive. Decide whether a re-profile that finds nothing removes a prior verdict.
  4. **Detector scope.** Only email and encoded exist. Adding phone, SSN, card or IP regexes is new detection, which the issue says it is not about. Note also that SQL evidence is the top 20 values by frequency, not a row sample.
  5. **Lineage.** Decide whether profiler verdicts propagate. I recommend no; only warehouse verdicts do.
