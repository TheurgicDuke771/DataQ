### 6. `backend/app/db/models.py` — `WorkspaceHealth` docstring vs actual service behavior

&gt; "`alerted_at` is written **after** a FAILING publish succeeds and cleared after the RECOVERED publish, **exactly like its per-connection sibling**. ... The row also serves as the cross-replica claim: the API-side check takes it `FOR UPDATE SKIP LOCKED`, so two API replicas never double-send."

The "written after a FAILING publish succeeds / cleared after RECOVERED" half checks out against `workspace_health_service.run_poll_staleness_check` (publish happens, *then* `flag.alerted_at` is mutated, *then* commit — an exception from publish leaves the flag untouched).

&gt; "**The send is dispatched, never awaited (#842).** It used to run synchronously inside the connection loop inside the beat task: Teams (10s) + Slack (10s) + SMTP (15s) per crossing... ten connections bolted ~6 minutes of blocking sends onto a task that beats every 10 minutes, delaying the ingest it exists to perform and risking overlapping beats."

It claims the edge with a fast atomic conditional `UPDATE ... WHERE health_alerted_at IS NULL` (commits immediately), then *dispatches a separate Celery task* to do the actual (slow, network-bound) publish; if that publish fails, a follow-up statement clears the claim.

The new `workspace_health_service.run_poll_staleness_check`, by contrast, takes `WorkspaceHealth` via `SELECT ... FOR UPDATE SKIP LOCKED` and holds that row lock **across the synchronous, multi-channel `publish_poll_staleness` call** (sequential `httpx.post` to Teams/Slack + SMTP send in `email.py`) before committing — i.e., it holds a Postgres row lock open for however long three network sends take, inside the same DB transaction, which is exactly the blocking-inside-a-transaction shape #842 was written to eliminate for the per-connection path. The end *state* (alerted_at set iff a publish actually succeeded) is equivalent, but the claiming/locking *mechanism* is materially different — "exactly like" overstates the equivalence and glosses over a design regression relative to the precedent the docstring cites as its model.</result>

## **Issue 1064**

**Title:** S3 asset identity collides across endpoints once S3-compatible stores are supported

**Body:**

Found while implementing #1063 (S3-compatible endpoints). Filing rather than fixing inside that PR: the fix changes an **asset namespace**, which is a persisted identity that lineage, incidents and scorecards hang off, so the convention deserves its own decision rather than riding along.

## The defect

`_resolve_s3` in `backend/app/services/asset_identity.py` derives the asset namespace from the bucket alone:

```python
namespace = f"s3://{bucket}"
```

That was **sound before #1063**, because every `s3` connection was AWS and AWS bucket names are globally unique — the bucket *was* a global identity.

Once a connection can carry an `endpoint_url`, bucket names are only unique **within an endpoint**. Two different stores with the same bucket name now resolve to the same `AssetIdentity`:

- AWS bucket `landing` → `s3://landing`
- MinIO at `https://minio.internal:9000`, bucket `landing` → `s3://landing`

## Failure scenario

An operator monitors an AWS bucket `analytics` and an on-prem MinIO bucket also named `analytics`. Both connections resolve to the asset `s3://analytics`, so DataQ merges them into **one** asset row. The consequences are all silent:

- the asset scorecard aggregates checks from two unrelated datasets into one score;
- lineage edges from both stores land on the same node, producing a graph that shows a dependency that does not exist;
- an incident raised on one store is attributed to the asset the other store also owns.

Nothing errors — the platform simply reports confidently about a dataset that is two datasets.

## Constraints on the fix

- **The AWS namespace must not change.** `s3://{bucket}` is the OpenLineage naming-spec form for AWS and is already persisted on `assets` rows in production; changing it would fork every existing S3 asset and orphan its lineage and incidents — the stability property `_resolve_iceberg` documents in the same module.
- So the endpoint host should only participate when `endpoint_url` is **set**, which is also why fixing it early is cheap: no S3-compatible connection exists yet, so there is nothing to migrate today. That window closes as soon as anyone creates one.
- The convention needs picking deliberately (OpenLineage does not standardise the S3-compatible case; candidates include folding the endpoint host/port into the namespace).

## Scope

- `backend/app/services/asset_identity.py::_resolve_s3`
- a test asserting that two connections with the same bucket and **different** endpoints resolve to different identities, and that an endpoint-less AWS connection still resolves to exactly `s3://{bucket}`.

## 2. The orphan-asset sweep (#770) — CRITICAL for #919

**`backend/app/services/asset_service.py:232-310`**, `sweep_orphan_assets(session, *, retention_days, now=None, chunk_size=500)`. Wired via **`backend/app/worker/tasks.py:913-933`** (`@celery_app.task(name="sweep_orphan_assets")`, daily beat entry `backend/app/worker/celery_app.py:138`).

**Exact deletion predicate** (line 286-291):
```python
candidate_chunk = (
    select(Asset.id)
    .where(Asset.last_seen &lt; cutoff, *_sweep_guard_clauses())
    .limit(chunk_size)
    .scalar_subquery()
)
```
where `cutoff = now - timedelta(days=retention_days)` and `_sweep_guard_clauses()` (lines 66-72) builds one `NOT EXISTS` per registry row in `_SWEEP_REFERENCE_GUARDS` (lines 55-63):
```
("suites", "asset_id")
("runs", "asset_id")
("lineage_edges", "upstream_asset_id")
("lineage_edges", "downstream_asset_id")
("incidents", "asset_id")   # #761
```
So a row is swept iff: `last_seen &lt; cutoff` **AND** it has zero rows in suites/runs/lineage_edges(either end)/incidents referencing it. `retention_days &lt;= 0` disables the sweep entirely (line 279-280, returns 0).

**Answer for #919**: **Yes** — an inventory-synced asset with no suite, no run, and no lineage edge is architecturally indistinguishable from an orphan by this predicate; it *is* a sweep candidate. It is **not** deleted immediately, and it is **not permanently safe by omission** either — it survives only as long as the inventory sync keeps re-upserting it (refreshing `last_seen`) more often than `retention_days` (default 30, see §7). If the inventory sync job is periodic and outlives `ASSET_ORPHAN_RETENTION_DAYS`, the row stays alive indefinitely via `last_seen` refresh; if the sync stops (e.g. the table is dropped, or the sync itself breaks), the row ages out and is swept after 30 days — same fate as any other now-unreferenced asset, which is the intended accrete/retire posture. **Design implication**: #919 needs its own periodic re-sync cadence (or the sweep needs a 6th guard, e.g. an `assets.source = 'inventory'` flag) if inventory-only assets should be exempt from ever expiring even when the source table has been dropped from the warehouse but not yet detected as such. Currently there is no such flag/guard — the registry (`_SWEEP_REFERENCE_GUARDS`) is enforced by a schema-introspection test (`test_every_asset_fk_has_a_sweep_guard`) that fails the build if a new FK into `assets.id` lacks a guard, but a non-FK provenance tag (like "this came from inventory sync") would need a deliberate design decision, not just a new column.

**`backend/app/services/asset_identity.py`** — pure resolver, `resolve_asset_identity(conn_type, config, target) -&gt; AssetIdentity(namespace, name)`:

| Type | namespace | name |
|---|---|---|
| `snowflake` | `snowflake://{normalize_snowflake_account(account)}` (lines 137, 81-103) | `DB.SCHEMA.TABLE`, case-folded via `_normalize_part` (Snowflake upper unless quoted) (`format_snowflake_name`, lines 106-114, 130-139) |

Orchestration types (`adf`/`airflow`/`dbt`) raise `ValueError` (line 78) — no identity, since they're never suite datasources; callers wrap this fail-soft.

**Case-folding rule** (`_normalize_part`, lines 228-247): a double-quote-wrapped (Snowflake) or double-quote/backtick-wrapped (UC) segment keeps its inner case verbatim once quotes are stripped ("engine-returned case for a quoted identifier"); unquoted folds to the engine's default (Snowflake upper, UC lower). This is the **same function** used by both the suite-target resolver here and the dbt-manifest canonicalizer (`lineage/edges.py`) and the warehouse-native pull (`lineage/warehouse_snowflake.py:_identity`/`_database`, lines 196-219) — "so identifiers match byte-for-byte" — this is the shared discipline #823 established (see below). **An inventory sync must reuse this exact module** (`resolve_asset_identity` or its per-type helpers) to avoid forking identity rules a second time.

**#823 identity-resolution discipline** (from `docs/progress.md`, not inline comments): #823 proved the OpenLineage "byte-for-byte join" premise was *half* wrong — feeding a real dbt `manifest.json` through real `openlineage-dbt` into real Marquez emits `DATAQ_DB.ANALYTICS.mart_order_revenue` (lower table name) while DataQ's asset identity resolver produces `DATAQ_DB.ANALYTICS.MART_ORDER_REVENUE` (upper) — **namespace joins, name does not**. This is why `WarehouseLineageProvider` (Snowflake/UC native pull, `warehouse_snowflake.py`) was built as a **separate seam** from the catalog `LineageProvider` (dbt/Marquez pull) — the warehouse path returns identifiers already in the engine's own case (straight from `ACCOUNT_USAGE`/`information_schema`), so there is "no fold/enumerate step and the #823 identity-drift class cannot arise there." **Design implication for #919**: an inventory sync reading directly from the warehouse's own catalog views (like the warehouse-lineage provider does) would be immune to the #823 drift; one built by re-deriving names through `asset_identity.py`'s fold rules from a config-driven target would need the same scrutiny #823 gave the dbt-manifest path.

**Where would an inventory-synced table get its identity from?** Two options visible in the codebase's own precedent: (a) mirror `warehouse_snowflake.py`'s pattern — read `database`/`schema`/`table` straight off `INFORMATION_SCHEMA`/`ACCOUNT_USAGE` in the engine's native case and build `AssetIdentity` directly (no fold), or (b) call `resolve_asset_identity(conn_type, connection.config, {"schema":..., "table":...})` per discovered table, which folds case per the OL rules. (a) is what #823 already validated as safe; (b) risks the same class of drift #823 found if the discovered case doesn't match what the engine's catalog actually returns.

**#1064 S3 endpoint-collision — confirmed, lives in this exact code**: `_resolve_s3` (`asset_identity.py:167-171`):
```python
def _resolve_s3(config, target) -&gt; AssetIdentity:
    bucket = _require(config, "bucket", "s3", "config")
    namespace = f"s3://{bucket}"
    ...
```
The namespace is keyed **only on bucket name** — no `endpoint_url` (added in #1065 for MinIO/Ceph/R2/Wasabi/Backblaze support) is folded into identity. Documented explicitly in `docs/datasources-checks.md:49-55`: *"An asset's identity is currently derived from the bucket name alone... Two connections pointing at different stores that share a bucket name therefore resolve to the same asset, merging their scorecards, lineage and incidents — tracked as #1064. Until it is fixed, keep bucket names distinct across endpoints."* Relevant to #919 if inventory sync widens S3/MinIO table discovery — the collision risk scales with however many buckets-with-same-name-different-endpoint exist.

### 1. HIGH — filter-after-LIMIT ordering defect silently breaks the cap-honesty guarantee (violates ADR 0040 §5's "no-silent-caps rule")
