## Altitude

**1. `backend/app/worker/celery_app.py` — one-off patch, not a general mechanism**
```python
task_routes={"llm_invoke": {"queue": LLM_QUEUE_NAME}},
```
This hardcodes a single task-name → single-queue mapping. It solves "llm_invoke got false-reaped behind run_suite" but not the general problem "any long-running task type starves behind run_suite's default queue." Celery natively supports `task_routes` as a dict of *patterns* (or a routing function), and separately supports `task_queue_max_priority`/per-message priority — either would express "route anything that isn't a suite run off the shared queue" once, instead of per-task-name. As written, the *next* slow task class (the PR body's own framing implies more will come) requires: a new `task_routes` entry, and editing all 4 deploy artifacts' `-Q` flag again. Nothing in the diff generalizes past task name `"llm_invoke"` — this is the second special-cased queue this codebase will need to hand-wire from scratch when the third one shows up.

**2. Queue identifier duplicated as a raw string across 5 files with no shared source of truth**
`LLM_QUEUE_NAME = "llm"` is defined once in Python, but is never referenced by the deploy artifacts — `ecs.tf`, `containerapps.tf`, `docker-compose.ghcr.yml`, and `docker-compose.yml` each independently hardcode the literal `-Q celery,llm` string. Nothing enforces that these 5 occurrences (1 Python constant + 4 CLI-flag literals) stay in sync; a future rename of the queue, or an accidental typo in one of the 4 deploy files, is caught by nothing — the new test (`test_llm_invoke_routes_to_its_own_queue`) only asserts the Python side. The comments are the only synchronization mechanism.

**3. `deploy/README.md` documents the deploy-coordination bug rather than closing it, which is inconsistent with how this project has handled the same class of bug before**
The added note says a worker `command` change "sits inert... until someone runs `tofu apply` separately" and that shipping the routing side "without applying the matching command change... means the worker silently never consumes the new queue." That's exactly the shape of bug this project has previously fixed at the root, not just documented: CLAUDE.md's own history records `#1355 → #1378` (CloudFront origin-secret enforcement moved into nginx config after a docs-only description of it was found not to hold) and `#1363 → #1376` (`ssl_cert_reqs=required` made an **app-level default** on any `rediss://` URL, specifically so a deploy-ordering mistake couldn't silently break Celery again). Both of those were the direct precedent for "a coordination gap between image-roll and Terraform-apply is a class of bug we fix in code/pipeline, not in a runbook note." Here, the PR leaves the actual hazard — a worker running with a stale command array, silently never draining `llm` — live and undetected, exactly the "silently never consumes messages queue forever with no error" failure the note itself calls out. A cheap alternative that would have closed this at the right altitude: emit a queue name from the worker on startup (or a `/healthz`-adjacent readiness check) that fails loudly if `llm` isn't in the consumed set, rather than trusting every future deploy operator to read this README paragraph.
