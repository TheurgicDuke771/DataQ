## 4. Existing CSS custom-property / design-token layer

Yes — there is a partial one, and it's explicitly future-proofed for exactly this: **`frontend/src/styles.css`** (lines 1–25) defines a `:root { --dq-primary; --dq-primary-soft; --dq-selected-bg; --dq-row-hover; --dq-canvas; --dq-border; --dq-ink; --dq-shadow-rest; --dq-shadow-hover; --dq-ease; --dq-motion-fast; --dq-motion-base; }` block, with a comment stating: *"Keeping them semantic means a post-v1 dark theme can override this one block (e.g. `:root[data-theme='dark']`) and the whole CSS layer inherits for free."* — i.e., the CSS layer was designed with this issue in mind and is a small, contained, easy override target (~7 color tokens + 2 shadow tokens).

However, this CSS-variable layer is a **separate, parallel system** from `theme.ts`'s `BRAND`/`appTheme` — they're documented as "mirrors" of each other but there's no single source of truth; both would need updating for a dark variant, and nothing currently reads CSS variables from JS (or vice versa) to keep them in sync. Everything else (the antd `ConfigProvider` tokens in `theme.ts`, and the ~10 files importing `BRAND` for inline `style={{}}`) bypasses this CSS layer entirely and goes through JS constants + inline styles instead. So: **three parallel theming surfaces** exist today — (a) antd `ThemeConfig` (`appTheme`), (b) the `BRAND`/`SHELL` JS constants consumed via inline styles in ~10 files, (c) the `--dq-*` CSS custom properties in `styles.css` — none of which currently talk to each other or to a runtime "which mode" signal.
