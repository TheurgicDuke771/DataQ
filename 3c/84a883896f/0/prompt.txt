  ## Finding 1 — `aria-label` on `ChecksOutcomeTag` sits on a role-less `<span>` and is likely never announced (real defect, hits the PR's own purpose)
  
  **File:** `frontend/src/components/shared/StatusTag.tsx:69-77` (the `Tag ... aria-label={...}` in `ChecksOutcomeTag`).
  
  Verified against `node_modules/antd/es/tag/index.js` (lines 164-176): antd v6 `Tag` renders `TagWrapper = href ? 'a' : 'span'`, and none of these call sites pass `href`, so the DOM node is a bare `<span>` with no `role` attribute at all (i.e. it gets the implicit ARIA role `generic`). Per the ARIA specification, `role=generic` is defined with **"Name from: prohibited"** — browsers' accessibility-tree pruning collapses a plain, non-focusable `<span>`/`<div>` with no qualifying role into its parent's inline text, discarding any `aria-label` on it. This is a well-documented, testable footgun (Chrome DevTools' Accessibility panel shows such nodes as "Ignored"/merged, dropping the label). The fix used elsewhere for exactly this shape is to give the wrapper an explicit naming-capable role (`role="img"`, `role="group"`, or `role="text"`) or to add visually-hidden text as a real child node instead of relying on `aria-label` on a generic span.
  
  This is the one place in the PR that carries a *composed* announcement ("1 of 2 checks passed, worst result critical") that isn't reconstructable from icon+text alone, so if the label is dropped, screen-reader users get exactly the "colour-only" experience (icon name + raw ratio, see Finding 2) that WCAG 1.4.1 was meant to fix — the PR's own stated goal.

  ## Finding 2 — Icon glyphs carry their own `role="img"` + literal icon-name `aria-label`, producing noisy/misleading announcements adjacent to the status text
  
  **File:** `frontend/src/components/shared/StatusTag.tsx:17-32` (`RESULT_STATUS_ICONS`/`RUN_STATUS_ICONS`), consumed at lines 44 and 52.
  
  Verified in `node_modules/@ant-design/icons/lib/components/AntdIconLight.js`: every `@ant-design/icons` glyph renders `<span role="img" aria-label={icon.name} ...>`, where `icon.name` is the kebab-case icon identifier (`check-circle`, `warning`, `close-circle`, `fire`, `minus-circle`, `exclamation-circle`, `clock-circle`, `sync`, `stop`). `StatusTag.tsx` passes these icons straight through as the `Tag`'s `icon` prop with no `aria-hidden` applied, so a screen reader landing on a tag whose parent-level `aria-label` is *not* honored (Finding 1) will fall back to composing the accessible name from content and read e.g. **"fire 1/2"** for a critical outcome, or **"check-circle succeeded"** / **"sync running"** — noise at best, actively confusing at worst ("fire" is not a status word a user will map to "critical"). Since the adjacent text (`{status}` or `{passed}/{total}`) already conveys the same information, these icons should be `aria-hidden="true"` (i.e. pass `aria-hidden` through to the icon element, or wrap with `aria-hidden` on a span), letting the Tag's own text or `aria-label` be the sole accessible name.
  
  Note on the unit test (`frontend/tests/components/StatusTag.test.tsx:15,430`): it reads `.anticon`'s `aria-label` attribute directly off the DOM via `querySelector`, not through the accessibility tree. Adding `aria-hidden="true"` to the icon would **not** break this test — the attribute stays in the DOM and `getAttribute('aria-label')` still returns it — but it does mean the test isn't actually proving anything about what assistive tech announces, only that each status keeps a distinct DOM marker. Worth knowing if/when Finding 2 is fixed.
