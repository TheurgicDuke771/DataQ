### 6. `backend/app/db/models.py` — `WorkspaceHealth` docstring vs actual service behavior

&gt; "`alerted_at` is written **after** a FAILING publish succeeds and cleared after the RECOVERED publish, **exactly like its per-connection sibling**. ... The row also serves as the cross-replica claim: the API-side check takes it `FOR UPDATE SKIP LOCKED`, so two API replicas never double-send."

The "written after a FAILING publish succeeds / cleared after RECOVERED" half checks out against `workspace_health_service.run_poll_staleness_check` (publish happens, *then* `flag.alerted_at` is mutated, *then* commit — an exception from publish leaves the flag untouched).

But **"exactly like its per-connection sibling" is not accurate as a mechanism claim**, and the difference matters. The per-connection sibling (`backend/app/worker/tasks.py`, `_alert_on_health_change` / `publish_connection_health`) deliberately does NOT hold a lock across the publish call — its own docstring explains why:
&gt; "**The send is dispatched, never awaited (#842).** It used to run synchronously inside the connection loop inside the beat task: Teams (10s) + Slack (10s) + SMTP (15s) per crossing... ten connections bolted ~6 minutes of blocking sends onto a task that beats every 10 minutes, delaying the ingest it exists to perform and risking overlapping beats."

It claims the edge with a fast atomic conditional `UPDATE ... WHERE health_alerted_at IS NULL` (commits immediately), then *dispatches a separate Celery task* to do the actual (slow, network-bound) publish; if that publish fails, a follow-up statement clears the claim.

The new `workspace_health_service.run_poll_staleness_check`, by contrast, takes `WorkspaceHealth` via `SELECT ... FOR UPDATE SKIP LOCKED` and holds that row lock **across the synchronous, multi-channel `publish_poll_staleness` call** (sequential `httpx.post` to Teams/Slack + SMTP send in `email.py`) before committing — i.e., it holds a Postgres row lock open for however long three network sends take, inside the same DB transaction, which is exactly the blocking-inside-a-transaction shape #842 was written to eliminate for the per-connection path. The end *state* (alerted_at set iff a publish actually succeeded) is equivalent, but the claiming/locking *mechanism* is materially different — "exactly like" overstates the equivalence and glosses over a design regression relative to the precedent the docstring cites as its model.</result>
