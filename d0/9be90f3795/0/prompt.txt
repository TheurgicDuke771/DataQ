<result>Reviewed the diff, migration, and `run_service.py` 1276–1465 in the worktree. All the flagged efficiency problems are real and verifiable from the code. Six findings, ordered by severity.

## Finding 1 — Index docstring claim is false: the partial index retains every passing-check row forever

**File:** `backend/alembic/versions/fbf4fe92e295_add_results_unpurged_created_index.py` lines 20–26 (same claim repeated in `backend/app/db/models.py` lines 862–866, "small, shrinking working set")

**Summary:** "the index only ever covers the sweep's actual working set, not the whole table" does not hold — the index asymptotically covers ~the whole table.

**Failure scenario:** A row leaves the partial index only when `sample_failures_purged_at` is stamped. But the first purge half's `jsonb_typeof(sample_failures) IS NOT NULL AND != 'null'` guard (run_service.py:1427–1429) permanently excludes every row whose `sample_failures` is SQL NULL — i.e. **every passing check's result, the majority of the table** — so those rows are never stamped and never leave the index. The index therefore grows linearly with total results written, dominated by never-eligible entries. Concretely: every daily sweep's index range scan (`created_at &lt; cutoff` covers all history) must heap-fetch every one of those dead entries to evaluate the typeof guards (typeof can't be answered from an index storing only `created_at`), so the daily sweep is O(all historical passing rows) every day — not O(the day's expired crop) as the migration claims. The index only excludes already-purged rows, the *minority* on a passing-dominated table, so the headline perf claim of the PR largely evaporates.

**Fix:** put the typeof guards into the index predicate — `WHERE sample_failures_purged_at IS NULL AND sample_failures IS NOT NULL AND jsonb_typeof(sample_failures) &lt;&gt; 'null'` — which the sweep's predicate still implies. Then never-eligible rows never enter the index, and it genuinely shrinks to the working set.

## Finding 2 — Batched loop re-scans the ever-growing dead prefix per chunk: catch-up is superlinear

**File:** `backend/app/services/run_service.py` lines 1329–1347

**Summary:** Each chunk's `SELECT id ... LIMIT chunk_size` restarts the index scan from the bottom of the `created_at` range, re-skipping all never-eligible entries every iteration — no keyset progression.

**Failure scenario:** Never-eligible (passing-row) entries below cutoff don't shrink between iterations (Finding 1), and eligible entries interleave with them by `created_at`. Chunk *k* must skip past roughly `k·chunk_size·(P/E)` dead entries (P = never-eligible rows below cutoff, E = eligible backlog) before assembling its 500 IDs, each skip a heap fetch to evaluate the typeof filter. Summed over `B = E/500` chunks that is **~P·E/1000 heap fetches**. Concrete: P = 2M passing rows, E = 100k backlog → ~2×10⁸ row visits across 200 chunks, versus the pre-PR single seq scan visiting ~2.1M rows once — the "catch-up run … which is precisely the case the AC's 'no lock-contention regression' check targets" (comment at 1281–1284) is exactly the case this makes ~100× *worse* in total I/O. Fixing the index predicate (Finding 1) collapses this, since purged rows then leave the index and each rescan starts at the first live entry; keyset pagination (`ORDER BY created_at, id` + resume-after cursor) is the belt-and-braces alternative.

## Finding 3 — The observed_value half cannot use the new index at all; batching turned 1 full scan into N full scans

**File:** `backend/app/services/run_service.py` lines 1438–1445

**Summary:** The second half's predicate (`created_at &lt; cutoff AND jsonb_typeof(observed_value-&gt;'observed_value') = 'array'`) has no `sample_failures_purged_at IS NULL` term, so it does not imply the partial index's predicate — Postgres will never use `ix_results_unpurged_created` for it. There is no other `created_at` index.

**Failure scenario:** Every chunk of the observed_value half is a sequential scan (LIMIT lets early chunks stop early, but the final iteration — which always runs, that's the loop's exit condition — scans the entire table). For an observed_value catch-up backlog of E rows, the pre-PR code did exactly **one** full scan; this PR does up to **⌈E/500⌉ + 1** full scans. The PR regressed the very half it claims to have indexed. Fix: a second partial index `ON results (created_at) WHERE jsonb_typeof(observed_value-&gt;'observed_value') = 'array'` — small by construction (only set-oriented expectations produce the array shape) and exactly implied by this half's predicate.

## Finding 4 — `_purge_column` docstring's "index makes the extra scan pass cheap" is a broken perf claim

**File:** `backend/app/services/run_service.py` lines 1313–1314

**Summary:** The justification for keeping two separate UPDATEs ("The daily 01:17 UTC cadence and the `ix_results_unpurged_created` partial index (#323) make the extra scan pass cheap") is false for one of the two passes.

**Failure scenario:** The "extra scan pass" being excused is precisely the observed_value UPDATE — the one that cannot use the index (Finding 3) and seq-scans daily. The rationale recorded in the code for an architectural choice (two UPDATEs vs one CASE-based UPDATE) rests on an index benefit that doesn't exist for that pass; the next person reading this will wrongly believe both halves are indexed. Either add the second partial index or correct the claim.

## Finding 5 — Extra empty round-trip when backlog is an exact multiple of chunk_size

**File:** `backend/app/services/run_service.py` lines 1342–1346

**Summary:** Exit sentinel is `affected &lt; chunk_size`, so a backlog of exactly `k·chunk_size` runs one additional iteration that selects and updates nothing.

**Failure scenario:** The wasted iteration is not just a round-trip: for the observed_value half it is **one additional full sequential scan of `results`** (Finding 3), and for the sample_failures half one additional full walk of the dead index prefix (Finding 2) — the emptiest iteration is the most expensive one, because finding zero matching rows means exhausting the entire candidate range. Also note the loop *always* runs at least once even when nothing is eligible (steady state for the observed_value half most days is 0 rows → a daily full seq scan to conclude "nothing to do" — pre-existing shape, but the PR's docstrings now describe it as cheap). Cheap mitigation for the multiple-of-chunk case: run the SELECT first and skip the UPDATE when it returns no IDs, or exit on `affected == 0` after a `chunk_size`-sized batch only when a follow-up probe is free — but the real fix is the indexes above, which make the empty pass cheap for real.

## Finding 6 — The new index disables HOT updates for the purge and taxes every result insert

**File:** `backend/alembic/versions/fbf4fe92e295_add_results_unpurged_created_index.py` line 70–71 (index definition)

**Summary:** Two standing costs the migration docstring doesn't account: (a) `sample_failures_purged_at` now appears in an index *predicate*, so every purge UPDATE is HOT-disqualified; (b) every result INSERT (all new rows have `purged_at` NULL) must add an entry to this index.

**Failure scenario:** (a) Before this PR no index referenced `sample_failures` or `sample_failures_purged_at`, so purge UPDATEs could be HOT — heap-only, no index maintenance. Now each purged row writes new index tuples into `ix_results_run_id`, `ix_results_check_id`, and the new index, tripling per-row write amplification on exactly the bulk operation the PR set out to lighten. (b) The insert-path tax funds an index whose entries, per Finding 1, mostly never earn their keep (never-eligible passing rows sit in it forever). Both costs become acceptable — small index, few entries — once the typeof guards move into the index predicate (Finding 1's fix), because then passing-row inserts skip the index entirely and only sample-bearing rows pay. As shipped, the hottest write path in the system (`results` insert, one per check per run) pays for an index that doesn't deliver its claimed benefit.

---

**Bottom line for the PR's perf claims:** the batching-for-lock-bounding part is sound in shape, but the index as specified doesn't deliver the claimed working-set bound (Finding 1), the chunk loop makes catch-up sweeps asymptotically *worse* than the single UPDATE it replaced (Findings 2, 3), and the second purge half is entirely unindexed despite docstrings implying otherwise (Findings 3, 4). The coherent fix is one index-predicate change plus one additional partial index; both are implied by the sweeps' own WHERE clauses and require no code change in `_purge_column`.</result>

## Batching design — and how mixed types are handled

**A rank driver LEFT-joined to one derived table per column**, not a `UNION ALL`:

```sql
SELECT r.rn, t0.value AS v_0, t0.freq AS f_0, t1.value AS v_1, t1.freq AS f_1, …
FROM (SELECT 1 AS rn UNION ALL SELECT 2 AS rn …) AS dq_ranks r
LEFT JOIN (SELECT ROW_NUMBER() OVER (ORDER BY count(*) DESC, c0) AS rn,
                  c0 AS value, count(*) AS freq
           FROM tbl WHERE c0 IS NOT NULL GROUP BY c0
           ORDER BY count(*) DESC, c0 LIMIT n) AS dq_top_0 ON dq_top_0.rn = r.rn
LEFT JOIN (…) AS dq_top_1 ON dq_top_1.rn = r.rn
ORDER BY r.rn
```

Each derived table is *exactly* the query `build_top_values_query` already built, plus a `ROW_NUMBER()` on the same ordering expression — which is both the join key and what restores per-column order (ties included) without re-sorting values in Python, where string collation wouldn't match the warehouse's. All SQLAlchemy Core; the connection's dialect quotes everything.

**Mixed types are handled by never unifying them** — each column keeps its own output column and its own type, so NUMERIC arrives as `Decimal` and TIMESTAMP as a datetime.

**The `UNION ALL` shape was built first and is the trap the issue flagged.** A union unifies branch types, so all values land in one `value` projection (Postgres refuses `integer`/`text`; Snowflake silently coerces to `VARCHAR`). Per-column value slots padded with `NULL` **do not rescue it**: an untyped `NULL` resolves pairwise left-to-right, so in a left-deep union tree two padding slots settle on `text` before the branch owning the slot is reached — Postgres rejected it with `UNION types text and timestamp without time zone cannot be matched`. It compiled cleanly and passed every SQL-text assertion; only running it found it.

Chunk size `_TOP_VALUES_BATCH = 25` is **measured**: on 50 cols × 50k rows the pass held ~270 ms at every chunk from 8–25 and jumped to ~820 ms as a single 50-way join (Postgres switches to its genetic optimiser at 12 relations). 25 puts the endpoint's own 50-column cap at exactly 2 batched round-trips.

## Fallback semantics

Any exception from a batch → the whole set is re-collected column-by-column via `_top_values_per_column` (kept as live code), logging `profile_top_values_batch_fallback` with the exception type so a perpetually-falling-back warehouse is visible rather than merely slow. A `DataQError` (bad identifier) is re-raised untouched, not retried. `top_n &lt; 1` routes directly to the per-column path; an empty column list issues nothing. If the retry also fails, the pre-existing 502 is unchanged.

## Design choices

**Where the spec lives** — on the suite's run-target JSONB (`{"sampling": {"strategy": "head"|"random", "rows": N, "seed": ?}}`), so no migration for the config side. `SampleSpec` sits in `datasources/base.py` beside `BatchSpec`; behaviour is a new pure module `datasources/sampling.py` (100% covered).

**Where sampled-ness is stored** — new nullable `results.sampling` JSONB (migration `4d23b47ee564`, up/down tested against Postgres), returned by `GET /runs/{id}` unredacted (it carries counts, not target data). **Per-result, not per-run**: within one run a volume monitor pushes down (exact) while the expectations beside it saw 100k of 5M — a run-level flag would have to lie about one. `sampled` is stored explicitly, so a "sample" larger than the dataset reports as the complete read it is instead of crying wolf on every small target. `null` = complete read, which is also what every pre-existing row means — no backfill.

**Caps** — `RUN_MAX_SCAN_BYTES` (128 MiB, flat files) and `RUN_MAX_SCAN_ROWS` (1.5M, UC). `0` disables the cap *and* its probe. Sampling **replaces** the cap rather than stacking with it.

**What UC pushes down** — freshness/volume were already scalar SQL aggregates and `schema_drift` already read `information_schema` (verified, unchanged). The gap was the *expectation* read: now `LIMIT rows+1` (head) or `TABLESAMPLE (p PERCENT) … LIMIT rows` sized from `COUNT(*)` (random). Not `ORDER BY rand()` (global sort) and not `TABLESAMPLE (n ROWS)` (Spark implements it as a plain LIMIT — a head sample wearing a random label).

Sampling is **refused at save time** on Snowflake/Iceberg rather than ignored, and never applied to freshness (a MAX over a sample is a *smaller* maximum → healthy data reported critically stale).

## PR A — what genuinely produces increments vs the affordance fallback

The premise in the brief was half right, and reading the code corrected it: **nothing landed incrementally before this PR**, not even the monitor kinds. `execute_run` collected every outcome and wrote them all in one `add_all` + commit at the end, so the flat-file runner's per-file iteration and the per-check monitor executors were invisible to the progress poll.

`_run_outcome_phases` now yields each unit of execution and `execute_run` commits per phase. Granularity is the engines' own:

| Kind | Granularity | Why |
|---|---|---|
| `schema_drift`, `anomaly`, `comparison` | **per check** — genuine increments | already run through a per-check executor |
| `expectation` | **one phase for the whole batch** | GX validates a suite atomically; no partial result exists inside it |
| `freshness`, `volume` | **one phase for the group** | `run_monitors` loads the frame once; splitting re-reads the object per monitor |

**I did not restructure the GX batch** — that's the issue's expensive option (30 checks → 30 reads to smooth a bar). So for a pure-expectation suite the fallback *is* the deliverable: server-measured `elapsed_ms` (additive on `RunProgressRead` + the MCP payload), and a drawer that shows a spinner + elapsed time and says why there is no percentage, instead of a 0% bar that reads as hung.

Two things the change forced, both worth a reviewer's eye:
- **`_discard_results`** — per-phase commits break "a failed/cancelled run has no results" for free, so it's now restored explicitly. Without it a partially-evaluated failed run would feed orphan `pass` rows into the health score.
- **`list_results` orders by the check, not the result** — commits gave `results.created_at` real execution-order meaning, which would have silently re-sorted the run-detail table by *engine*.
