  **Design** (new `backend/app/services/schedule_dispatch.py`; `tasks._dispatch_due_schedules` now just calls it):
  - **Batches of up to 500, one transaction each:**
    - claim with `SELECT … ORDER BY next_run_at LIMIT 500 FOR UPDATE SKIP LOCKED`;
    - load the batch's suites and connections in one query;
    - write all schedule advances in one `UPDATE … FROM unnest()` and all queued runs in one multi-row `INSERT`, then commit;
    - publish each run to the broker after the commit;
    - write all task ids back in one `unnest` UPDATE.
  - **Round trips:** statements per tick no longer grow with the due set — 10 due → 5 statements, 1k → 11, 10k → 101 (it was about 10 per schedule).
  - **Semantics kept:**
    - Exactly-once holds per batch: claim, advance and insert commit together.
    - Publishing strictly follows the commit, so a batch that rolls back never reaches the broker.
    - DST handling and no-backfill are unchanged: it still calls `cron.next_fire(after=now)` in the schedule's timezone, now computed once per `(cron, timezone)` per tick.
  - **Per-tick budget:** checked between batches. After 45 s it stops claiming and logs `schedules_dispatch_budget_exhausted` with the number still due; the next tick picks them up.
  - **Broker down:** after 3 publish failures in a row, the rest of that batch is marked failed without further attempts and the tick ends (`schedules_dispatch_stopped_broker_down`). Unclaimed schedules stay due. This was the one `/code-review` finding (low), fixed in the PR.
  - **Publishing is serial.** I tried an 8-thread publish pool and removed it: it deadlocked in about 1 of 20 bursts locally. The captured stack shows Celery's Redis result backend and a single `PubSub` lock that a garbage-collected `AsyncResult` re-enters.
  - **Perf rig:** the enqueue stub now sits on `dispatch_run`. The scheduler cases gain a `dispatch_statements` metric gated `strict`, so a return to one-schedule-at-a-time fails CI.
