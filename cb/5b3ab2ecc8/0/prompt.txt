`/Users/arijit/Coding/Python/DataQ/backend/app/core/secrets.py:559` uses `if self._role_id is None:` as the mode discriminator, but `/Users/arijit/Coding/Python/DataQ/.env.app.example:98-99` (added by this PR) ships `OPENBAO_ROLE_ID=` / `OPENBAO_SECRET_ID=` blank, and pydantic-settings resolves a present-but-empty env/dotenv value to `""`, not `None`. `_build_store` (`secrets.py:820-829`) passes it straight through.

This is the exact question you asked about the validator vs `_build_store` agreeing: **they do not.** The `Settings` validator `.strip()`s (`/Users/arijit/Coding/Python/DataQ/backend/app/core/config.py:409-410`), so `""` passes as "no AppRole"; `_build_store` uses bare truthiness and the store uses `is None`. Reproduced through the real dotenv path a fresh `scripts/setup.sh` produces (`setup.sh:103` does `cp .env.app.example .env.app`):

```
openbao_role_id = ''  | openbao_secret_id = ''
store._role_id  = ''  -&gt; AppRole mode engaged? True
GET conn-x -&gt; RAISED SecretStoreUnavailableError: OpenBao AppRole login failed: 400
```

The process **boots clean** and then every credential read, write and delete fails at runtime — the "dies mid-run in a worker" failure the ADR-0039 validator was added to prevent, reintroduced one layer down. It also hits the compose stack (api/worker take `OPENBAO_ROLE_ID` from `env_file: .env.app`). A whitespace-only pair (`"  "`) is a second flavour of the same bug: the validator strips it to "no AppRole", `_build_store`'s truthiness check sees two truthy values and passes.

Fix: normalise once at the boundary — `self._role_id = (role_id or "").strip() or None` (same for `secret_id`) in `__init__` — and make `_build_store` and the validator share that normalisation rather than each re-deriving it.

### 2. `delete()` is no longer fail-soft — a login failure escapes and can 500 a connection delete that already succeeded. **Real defect.**

`secrets.py:776` now routes through `_send` → `_headers` → `_current_token` → `_login_locked`, which raises `SecretStoreUnavailableError` (`secrets.py:606`, `614`). That is not an `httpx.HTTPError`, so `delete`'s `except httpx.HTTPError` (`secrets.py:777`) does not catch it. Reproduced with a sealed vault (503 on login):

```
delete:      RAISED SecretStoreUnavailableError: ... login failed: 503 — vault sealed
set:         RAISED SecretStoreUnavailableError  (not SecretWriteError)
_created_at: RAISED SecretStoreUnavailableError  (not None)
```

Three call sites document and depend on the fail-soft contract this breaks:
- `/Users/arijit/Coding/Python/DataQ/backend/app/services/connection_service.py:840-842` — *"fail-soft (delete never raises), so a store hiccup can't 500 a successful delete."* Now false: the row is already deleted and committed, so the user gets a 500 on a delete that succeeded.
- `/Users/arijit/Coding/Python/DataQ/backend/app/services/secret_sweep_service.py:301` — *"`delete` is fail-soft BY CONTRACT"*. The purge loop now aborts on the first orphan.
- `/Users/arijit/Coding/Python/DataQ/backend/app/services/notification_service.py:255,272` — post-commit orphan cleanup, same shape.

Two siblings of the same root cause:
- **`set()`** now raises `SecretStoreUnavailableError` where it used to raise `SecretWriteError`, so `connection_service.py:343/574/657` stop mapping it to the 502 `ConnectionSecretWriteError` and it becomes a generic 500.
- **`_created_at()`** (`secrets.py:498-501`) no longer degrades to `created_at=None`. Its docstring promises *"a metadata hiccup can never cause a delete"* — the safe direction is preserved by accident (the sweep aborts), but the documented degradation is gone.

This is the same family as the lesson recorded in the ADR-0039 review: callers branch on exception **type**, and a new type crossing a seam that previously only emitted two types breaks them silently.

## Important

### 3. The 403 re-login is not compare-and-swap — N concurrent threads produce N logins. **Real defect.**

`secrets.py:653-656` unconditionally calls `_forget_token()` on any 403. Measured with 8 threads released from a barrier against a permanently-403ing path: **9 logins**. Each thread also discards the token a peer just obtained. The `_send` docstring (`secrets.py:641-646`) promises *"exactly one retry ... more would turn a genuinely bad `secret_id` into a login storm against the vault"* — but that bound is per-call, not per-store, and the class is explicitly a process-wide singleton shared by FastAPI request threads and Celery workers, i.e. precisely the case where the promise fails.

Fix: capture the token value actually sent, and only clear if `self._auth_token` is still that value:
```python
sent = self._current_token()
response = self._client_lazy().request(method, path, headers={"X-Vault-Token": sent}, **kwargs)
if response.status_code == 403 and self._role_id is not None:
    self._forget_token_if_still(sent)   # CAS under _auth_lock
```

### 4. A least-privilege AppRole policy makes the orphan sweep re-login on every secret. **Real defect.**

Vault answers **403 for insufficient policy**, not only for a dead token — and the class docstring at `secrets.py:372-375` explicitly anticipates a policy lacking `read` on `&lt;mount&gt;/metadata/*`. `_send` treats every 403 as "token dead", so each `_created_at` costs an extra login plus an extra GET. Measured over 3 secrets:

```
list_secrets() -&gt; 3 x created_at=None
logins: 4  |  metadata GETs: 6     (expected: 1 login, 3 GETs)
```

Linear in mount size, and permanent for that deployment. Same root cause as finding 3; a CAS plus not retrying when the previous attempt already used a freshly-issued token fixes both.

### 5. Any lease ≤ 60s means a login on **every** request, forever — and a test enshrines it. **Real defect.**

`secrets.py:619-623` computes `expires_at = now + (lease - 60)`. For a hardened AppRole with `token_ttl=60s` (a reasonable production setting) that is already in the past at issue time, so `_token_is_stale()` is `True` on the very next call: 2 HTTP round-trips per credential resolution, permanently, on the hot path the `_client_lazy` docstring says matters.

`test_approle_renews_before_the_lease_expires` (`/Users/arijit/Coding/Python/DataQ/backend/tests/core/test_secrets.py`, the `lease_duration: 30` / `assert logins == 2` test) asserts this degenerate behaviour as correct. Fix: clamp, e.g. `effective = max(lease - MARGIN, lease // 2, 1)`.

### 6. `lease_duration` crosses a driver boundary and `isinstance(lease, int)` is too narrow. **Real defect (three variants, all reproduced, none tested).**

At `secrets.py:621`:
- `lease_duration: 3600.0` (a JSON float from a proxy or a non-OpenBao Vault build) → `isinstance(..., int)` is False → `_auth_expires_at = None` → **proactive renewal silently disabled for the whole process**. The feature degrades back to the reactive 403-retry it was built to replace, with no log line saying so. A string `"3600"` does the same.
- `lease_duration: true` → `isinstance(True, int)` is True, `int(True) == 1` → expires 59s in the past → login per request.
- `lease_duration: 10**19` → bare **`OverflowError`** propagates out of `get`/`set`/`delete`, caught by nobody (every caller guards `httpx.HTTPError`), breaking the type contract ADR 0039 decision 6 rests on. Worse, because `self._auth_token = token` is assigned at `secrets.py:618` *before* the expiry is computed at `:619`, the store is left caching a token against a stale `_auth_expires_at`.

This is the repo's own #953/#823 shape — the type comes from the server, and every fixture in this PR hands in a clean `int`. Fix: coerce inside a `try` accepting `int | float | str`, compute the expiry *before* assigning the token, and clamp to a sane range.

### 7. The redactor covers neither the vault token nor `secret_id` — and the ADR now asserts that it does. **Real defect (defence-in-depth + inaccurate doc).**

Measured against `/Users/arijit/Coding/Python/DataQ/backend/app/core/logging.py`:

```
key 'x-vault-token' in _PII_KEYS: False     key 'client_token': False
key 'secret_id'     in _PII_KEYS: False     key 'role_id':      False
scrub bare: 'X-Vault-Token: REDACTED'   -&gt; UNCHANGED
_redact_pii({'headers': {'X-Vault-Token': 'hvs.…'}, 'secret_id': 'abc123456'}) -&gt; UNCHANGED
```

`_BEARER_TOKEN_RE` matches `dq_live_`, JWTs and `bearer &lt;tok&gt;`, but an OpenBao token (`hvs.…` / `s.…`) matches none of them. The ADR text this PR edits retains *"the logger-level redactor ... covers `token` keys and bare token shapes"* — true only for the `token=` query-param form, which is not how this credential travels.

The store's own call sites are clean (`_login_locked` deliberately never logs `response.text`, and `show_locals=False` at `logging.py:135-136` closes the #536 traceback-locals vector). But #849's whole lesson is that call-site discipline is the half that fails, because a dependency does the logging. Adding `x-vault-token`, `client_token`, `secret_id` to `_PII_KEYS` — the mechanism that file itself calls *"the sturdier of the two … it cannot be fooled by a token SHAPE nobody anticipated"* — is a two-line change this PR should carry, and the ADR sentence should be narrowed to what is actually true.

## Test quality

### 8. The single most security-relevant line in the diff is untested. **Real gap.**

`secrets.py:598-609` deliberately logs only status/explanation because *"the body can echo the submitted secret_id on some error paths"*. `test_approle_login_never_logs_the_token_or_the_body` exercises only the **200** path — adding `body=response.text` to the `openbao_approle_login_failed` warning would fail nothing. Two further weaknesses in that test: the `secret_id` sentinel is `"sid"` (3 chars, collides trivially), and the assertion excludes the `openbao_approle_login` event from the haystack. Use a distinctive canary, assert over the full capture, and add a non-200 login case.

### 9. `test_approle_renews_before_the_lease_expires` passes, but not for the reason it claims.

With `lease_duration: 30` against a 60s margin the token is *already expired* at issue, so the test cannot distinguish "renews inside the margin" from "renews only once actually expired". It is not vacuous (setting the margin to 0 fails it), but the margin semantics — token still within lease, inside the margin, must renew — have **no** test, because `datetime.now(UTC)` (`secrets.py:579`, `620`) is called directly with no injectable clock. Same "passes, not for the right reason" shape as the five cases recorded in CLAUDE.md's lesson-of-the-week.

### 10. Nothing covers the contracts findings 1, 2, 3 break.

No test that `delete` stays fail-soft when the vault is down under AppRole; none that `set` still raises `SecretWriteError`; none that `_created_at` still degrades to `None`; **no concurrency test at all**, despite thread safety being the central design claim and the store being a documented process-wide singleton.

### 11. New validator branches untested, and existing validator tests are now partly environment-decided. **Real gap — this is how finding 1 got through.**

`_real_settings` (`/Users/arijit/Coding/Python/DataQ/backend/tests/core/test_secrets.py:392-398`) `delenv`s `SECRET_STORE`, `OPENBAO_ADDR`, `OPENBAO_TOKEN`, `OPENBAO_MOUNT`, `AZURE_KEY_VAULT_URL` — but **not** the two keys this PR adds. A developer or CI environment exporting `OPENBAO_ROLE_ID` would flip `test_settings_rejects_openbao_without_token_at_startup` from pass to fail: an outcome decided by the environment, not the test. Separately, none of the new `config.py:407-428` branches (partial AppRole → `ValueError`, AppRole-without-token accepted, blank-string role id) has a `Settings`-level test; only `_build_store` is covered, through a `SimpleNamespace` stand-in that by construction cannot produce the `""` real pydantic produces — the exact "the tests missed it by construction" pattern already recorded for #124.

**Boot-compat answer:** no existing deployment newly fails to *boot* — the validator is strictly more permissive than before except for the partial-AppRole rejection, and nothing had `OPENBAO_ROLE_ID` set before this PR. But finding 1 means deployments newly fail at *runtime*, which is the worse direction.

## Nits

12. **`config.py:407-408`** — message regression. The old code collected every missing name into one error (`"requires OPENBAO_ADDR and OPENBAO_TOKEN"`); the addr check now short-circuits, so an operator missing both fixes one, re-runs, and only then learns about the other.
13. **`secrets.py:749-751`** — the 403 retry re-POSTs `set`, and KV v2 `set` creates a new version, so it is not idempotent in version count. Benign in practice (a 403 means the write did not happen), but the `_send` docstring discusses the retry *bound* without saying anything about mutating-request safety; one sentence would close it.
14. **`secrets.py:581`** — `_auth_lock` is a plain `Lock`, so a future refactor routing the login through `_send`/`_headers` (a natural thing to reach for when fixing finding 2) deadlocks instantly. Either say "never call `_send`/`_headers` from here" explicitly, or use an `RLock`.
15. **`secrets.py:579`, `:620`** — interval math on wall-clock. An NTP step backwards makes an expired token read as fresh (self-heals via the retry); forwards forces a spurious login. `time.monotonic()` is the right clock for a duration.
16. **ADR 0039 decision 4** — now reads *"AppRole … is **deferred and filed**, not silently omitted — see Related"* immediately followed by *"**Phase 2 has since landed.**"* The first clause should go.
