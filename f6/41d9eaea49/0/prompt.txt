### 1. (High) `kind`-suffixed secret ref can collide with the primary ref, silently clobbering one credential

## Design chosen, and why

Custom-SQL checks on Unity Catalog now run against a **GX Databricks-SQL batch** (`context.data_sources.add_databricks_sql`), while every other expectation keeps the pandas DataFrame batch. `run_checks` partitions and merges outcomes back **positionally**, because `run_service` zips them onto its own check list.

I deliberately **did not** take the brief's preferred design (hand-rolled COUNT + capped samples over the databricks-sql engine). Reasons, in order of weight:

1. GX's own SQL datasource makes the semantics identical to the working Snowflake path **by construction** — `{batch}` substitution, 0 rows = pass, row count as `observed_value`, query error as operational `error`. A hand-rolled version is a second implementation of a contract free to drift.
2. **It adds no SQL-string interpolation of our own**, so there is no new injection surface. ADR 0019's guardrails are inherited unchanged rather than re-implemented — and I avoided asymmetric hardening (run-time re-validation on UC only) for the same parity reason.
3. No new dependency; `databricks-sqlalchemy` was already installed and used.
4. I proved it live **before writing production code**.

Consequently `sample_failures` stays `None` and `metric_value` stays NULL — matching Snowflake exactly (ADR 0019 §4). Populating `metric_value` on UC only would make the same check band differently per datasource; filed as #1202 instead.
