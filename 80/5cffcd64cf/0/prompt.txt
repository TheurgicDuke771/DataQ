**Exception types (ADR 0039 decision 6 — lines 111–138):**

This is **best-effort**, no-op on either exception type.

**For OTP (per ADR 0032 §7):** Must use the same `get()` call but surface errors to the caller (synchronous contract), not suppress them.

Cookie-relevant observations:
- **No `proxy_cookie_path`, no `proxy_cookie_domain`, no `proxy_cookie_flags`** anywhere in the template. `Set-Cookie` passes through unmodified. If the backend sets `Path=/api/v1` the cookie won't be sent on other paths — the backend should set `Path=/` (or add `proxy_cookie_path`). If the backend sets a `Domain`, it must match the browser-facing host.
- **`Host` is deliberately NOT set to `$host`** (lines 60-68 of the comment block) — it defaults to `$proxy_host` (the upstream). So the backend sees the *upstream* hostname, not the browser's. Any backend logic that derives a cookie `Domain` or a redirect from `Host` will be wrong; `X-Forwarded-Proto $scheme` (line 86) is the only signal for "was this HTTPS" — required for the `Secure` flag decision (ADR 0032 §3) and needs `uvicorn --proxy-headers` / `ProxiedHeadersMiddleware` on the backend to be honoured.
- Nothing strips `Cookie` on the request side — same-origin `/api/*` means the browser attaches it automatically, no `withCredentials` needed.
- `location = /config.js` has `Cache-Control: no-cache` (line 28); `location /` has `no-cache` (line 122) — index.html is never cached, so no stale-bundle risk when the mode flips.
- Dev path is different: `vite.config.ts:23-26` proxies `/api` and `/mcp` to `VITE_API_PROXY_TARGET`; Vite's `http-proxy` also passes `Set-Cookie` through but rewrites nothing — same considerations, plus dev is plain `http://localhost:3000` so a `Secure` cookie will be **dropped by the browser in dev** unless the backend conditions `Secure` on `X-Forwarded-Proto`/an env flag. ### 4. VERDICT — A per-EMAIL limit is NOT expressible in the current design without new plumbing. Service-level Redis counters are the cleaner path.

The middleware's policy function has the signature `_resolve_policy(path: str, bearer: str | None, ip: str, settings: Settings) -&gt; tuple[str, int, str]` (`rate_limit.py:335-337`). **Its only inputs are path, Authorization header, and client IP.** The body is never read anywhere in the file. Three concrete blockers:

1. **Body access in a `BaseHTTPMiddleware` dispatch is a known hazard.** `app.middleware("http")` wraps the function in Starlette's `BaseHTTPMiddleware` (FastAPI 0.139.2, `backend/requirements.txt:17`). Calling `await request.body()` in the dispatch drains the receive channel that `call_next` then hands downstream, so the OTP route would see an empty/hanging body unless you re-inject a replay `receive`. Doable, but it is real plumbing on the **innermost middleware that every single request on `/api` + `/mcp` + webhooks passes through** — you would be paying a body read (or at least a path check guarding it) on the hot path that ADR 0035 went out of its way to keep to one Redis round trip.

2. **It would break the class model's invariant.** Every existing key is derived from data that is cheap and *always present*; a body-derived key must handle malformed JSON, missing `email`, wrong content-type, and oversized bodies — all *before* FastAPI's validation has run (the limiter is deliberately pre-routing, per the test-file docstring at `test_rate_limiting.py:3-5`). Normalization (casefold/trim, the "normalized email" ADR 0035:102 asks for) would also have to be duplicated outside the Pydantic model that owns it.

3. **The dev/E2E kill switch (see §3) turns it off exactly where OTP flows are exercised.**

**Recommendation for #734:** split it.
- **In the middleware** (cheap, fits the existing design perfectly): add a fourth class, e.g. `auth`, matched on an `_AUTH_PREFIX` constant alongside `_WEBHOOK_PREFIX`, keyed `ip:{ip}` with its own much stricter cap (`RATE_LIMIT_AUTH_PER_MINUTE`). This is a ~6-line change to `_resolve_policy` plus one settings field, and it satisfies the "per-IP" half of ADR 0032's prerequisite. Note it must be checked *before* the `bearer is not None` branch (like `webhook` is) so a bearer-carrying request can't dodge the auth class.
- **Per-email must be service-level.** Do it in the OTP service after Pydantic has parsed and normalized the address, as a Redis counter on the same `rl:`-style fixed-window pattern. Precedent for a narrow, timeout-bounded, directly-constructed Redis client outside the middleware already exists at `/Users/arijit/Coding/Python/DataQ/backend/app/worker/beat_watchdog.py:94-115` (`_TickStore` Protocol + `build_store(redis_url)`), and that module's own comment (line 81) explicitly cites `core/rate_limit.py` as the pattern it copies. The `RateLimitStore` Protocol (`rate_limit.py:81-89`) and `InMemoryStore` (`:200-223`) are reusable as-is for the counting and for tests. Service-level also gets you the thing the middleware *can't* give you: a per-email counter that survives independently of `RATE_LIMIT_ENABLED`, so OTP brute-force protection stays on in dev/E2E and is testable end-to-end.</result>

### 1 — `_upsert_user` IntegrityError → 409
`IdentityConflictError(DataQError)`, `status_code=409`, `code="identity_conflict"`, raised after `db.rollback()`, mirroring `connection_service`/`share_service`. Covers `mcp/auth.py` too, since it goes through the same helper.

On the message/logging constraint: I put **nothing** identifying in either. The structured log carries `aad_object_id` only — `_PII_KEYS` covers both `aad_object_id` and `email`, so that field is redacted — while the *message* travels in the HTTP error envelope, which the redactor does not touch, so naming the colliding address there would leak workspace membership to anyone who guessed an email. `detail` is left empty for the same reason, and a test asserts all of it.

One thing worth flagging that the brief didn't call out: **the `db.rollback()` is load-bearing, not hygiene.** Without it the session stays in a failed transaction and the next statement raises `PendingRollbackError` — a "handled" 409 would still take the request down. It has its own test (`test_the_session_is_usable_after_the_conflict`).

New file `backend/tests/core/test_identity_conflict.py`, 5 tests, all DB-backed, **including the TestClient-level one you hoped for**: seeding a squatter row that holds the case-variant of `DEV_BYPASS_EMAIL` makes the dev-bypass authenticator fail on its own fixed `(oid, email)` pair, so `GET /api/v1/me` reproduces the production shape exactly and asserts 409, not 500.
